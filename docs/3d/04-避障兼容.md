# 04 · 与现有避障系统的兼容

> 本文回答：**3D 化之后，现有的全局绕障 / 编队骑过 / 局部侧让 / 碰撞分离怎么继续工作。**
> 结论先行：**避障的核心算法一行不改**，只换"喂给它的障碍集合"。这是本方案最大的兼容优势。

---

## 1. 现有避障的五层结构

| 层 | 位置 | 职责 |
|---|---|---|
| **① 全局绕障** | `pathfinding.ts:138-142` `avoidObstacles` → `routeAround`（可见图 + Dijkstra，四角节点，`margin = 0.6`） | 整条路径被挡时**重路由**（会丢失中间曲线造型） |
| **② 骑过判据** | `solver.ts:33-48` `canStraddle` | 让锚点忽略"编队骑得过去"的小障碍，避免为一个小箱子掰弯整条线路 |
| **③ 局部侧让** | `solver.ts:296-595` `groupInfluenceOffset`：侧向分流 / `latCenter` 整队绕 / `MAX_LAT_PUSH=6` 回退到世界轴推出 / `CLEAR=0.25` + `LEAD=1.0` 渐入 | 队员沿障碍两侧分流绕行 |
| **④ 二次兜底** | `solver.ts:575-593` | 对"编队期望 + 惯性甩动"的最终落点再测一次，保证无论如何不穿模 |
| **⑤ 碰撞分离** | `collision.ts:27-64` `separateSetAsset`（8 轮迭代）；`pathfinding.ts:38-66` `pushOut` / `pushOutAll`（4 轮） | set 之间推开；端点从障碍里推出 |
| **⑥ 缓存** | `path.ts:113` `routeCache`（≤256）、`solver.ts:205` `objectRouteCache`（≤128） | 都按几何 + `revision` 作 key |

### 精确调用点（决定改动范围）

| 障碍集合入口 | 调用点 |
|---|---|
| **`routeObstacles(state, objectId)`** | `solver.ts:75`（`basePosition` → ①全局绕障）<br>`solver.ts:222`（`objectRoute` → 组队路径 LUT）<br>`solver.ts:615`（`baseHeading`）<br>`WorldView.tsx:657`（橙色导航层可视化） |
| **`setRects(state)` 直调** | `solver.ts:360`（`groupInfluenceOffset` 内的 `const sets` → ③局部侧让 + ④二次兜底） |
| **`assetRect` 直调** | `collision.ts:13-14`（⑤ `footprintsOverlap`） |
| **`blockingAssets`** | `WorldView.tsx:688`（遮挡高亮）、`WorldView.tsx:2117`（CameraHud 遮挡指示） |
| **`separateSetAsset`** | `directorStore.ts:898`（拖拽 set）、`991`（新增 set）、`1086`（合并组） |

> **关键发现：障碍集合有 2 个入口，不是 1 个。** `routeObstacles` 和 `groupInfluenceOffset` 里的裸 `setRects` 是两条独立通路 —— 只改前者会导致"全局路线不绕了，但队员还在侧让"这种诡异行为。

## 2. 兼容支点：把"可达性过滤"插在障碍集合的最前端

新增一层更早的过滤：

```ts
// engine/ground.ts
/**
 * 真正"拦得住"该对象的障碍子集。
 * 能迈上去的、能跳过去的、能从下面穿过的，都不算阻挡。
 */
export function blockingRects(
  state: DirectorState,
  objectId: string,
  fromY: number,
  loco: Locomotion,
): Rect[]
```

过滤规则（对每个 `role === "set"` 的对象 `o`）：

| 条件 | 判定 | 理由 |
|---|---|---|
| `o.top ≤ fromY + loco.maxStep` | **排除** | 直接迈上去，不构成水平阻挡 |
| `maxStep < Δh ≤ maxJumpHeight` 且跨度在包络内 | **排除** | 跳过去，不应掰弯整条路径 |
| `o.bottom ≥ fromY + loco.height + clearance` | **排除** | 可从下方穿行 |
| `o.blocking === false` | **排除** | 语义开关（草丛、水面） |
| `topShape === "ramp"` 且坡度 > `maxSlopeDeg` | **保留** | 太陡 → 等同墙 |
| 其他 | **保留** | 真阻挡 |

然后：

```ts
export function routeObstacles(state: DirectorState, objectId: string): Rect[] {
  const o = state.objects.find((it) => it.id === objectId);
  const loco = locomotionOf(state, o);
  const fromY = baseYOf(state, o, /* segment 起点 */);
  return blockingRects(state, objectId, fromY, loco)
    .filter((r) => !canStraddle(state, o, r));
}
```

**这一个替换让 ① ② ③ ⑤ 全部自动获得 3D 感知。** 理由：现有代码已经有完全同构的先例 —— `canStraddle`（`solver.ts:33-48`）就是"把某些障碍从绕障集合里剔掉"，注释还写明了动因：

> "让**锚点**的全局路线规划忽略这类小障碍。否则哪怕一个小箱子，只要压在队伍行进线上，`pathfinding.avoidObstacles` 就会先用可见图 + Dijkstra 把整条线路掰弯绕开"

**我们只是增加了新的剔除判据。** 而且 `SegmentPaths`（`WorldView.tsx:657`）与求解共用 `routeObstacles`，所以橙色导航层自动保持一致 —— 这个"两边必须一致"的约束（代码注释明确警告过）不需要额外维护。

## 3. 跳过去 vs 绕过去的歧义（必须显式决定）

一个 0.9m 高的箱子横在路径上：**既能跳过去，也能绕过去。默认哪个？**

**建议：默认跳过去。** 理由：

1. 符合"路径是导演意图"的哲学 —— 作者画了一条直线，说明他想走直线
2. 绕行才是系统自作主张，而现有代码已经有绕行的先例，容易被过度触发
3. 导演若想绕，**加一个路点即可**（现有能力，零成本）

但必须给**反向逃生口**：对象上 `prefer: "walk-around"`，让某些物体强制绕行 —— 一片刺丛、一个水坑，你不会想让人跳进去。

并且 **UI 要显式展示这个选择**：跳跃徽标点开有「改为绕行」（见 [03 §5](./03-UI可达性提示.md#5-inspector-可达性面板)）。歧义可以存在，但不能是隐藏的。

## 4. 缓存 key 的陷阱（必须解决，否则性能崩）

**现状**：

- `segmentSignature`（`path.ts:115-119`）= `id | 起终点 | 路点 | 障碍矩形列表`
- `objectRouteCache`（`solver.ts:215`）key = `${revision}|${objectId}`

**陷阱**：3D 后 `blockingRects` 依赖 `fromY`，而 `fromY` **随时间和位置变化**（人可能在二楼，也可能在坑里）→ 障碍集合变成逐帧变量 → 缓存 key 退化成"每个时刻一份" → **缓存全废，且每帧重跑可见图 + Dijkstra**。

**解法：按段分类一次，段内固定。**

- 用**该 segment 的起点可达面高度**作为 `fromY` 来分类，段内不重算
- 把这个 `fromY` **量化**（`Math.round(fromY * 100)`）后加进缓存 key，保证同一高度区间能复用

**为什么安全**：一条 MOVE 段内 `baseY` 通常不变（除非带 `vertical` 弧线）。即使用弧线，用起点高度分类意味着**取该段最低处的判断** → 更多障碍被判为阻挡 → **路径更保守** → 绝不会穿模。

**已知误差**：如果一段内从地面爬到高处，低处的分类会让它绕一楼的墙。这是**保守方向的误差**，可接受。

**何时需要升级**：如果将来出现"一段内跨越很大高差且路径很长"的真实需求，就把分类按**高度分段**做（沿路径扫描 `groundHeightAt`，在高度区间边界处切成子段，每子段一份障碍集合）。**v1 不做。**

## 5. 两个障碍集合，两种职责（最容易搞错的地方）

`groupInfluenceOffset` 里的 `const sets = setRects(state)`（`solver.ts:360`）**同时**服务两件事：

| 用途 | 应使用的集合 | 理由 |
|---|---|---|
| **③ 侧向让位**（意图） | **可达性过滤后**的集合 | 一个该迈上去的台阶不该引发侧让 |
| **④ 二次兜底 push-out**（防穿模保证） | **全集**，但改 3D 严格相交 | 这是"无论如何不穿模"的地板，不能因为意图过滤而失效 |

**为什么全集兜底不会出问题**：因为它改成**3D 严格区间相交**判定。

- 台阶 `[0, 0.3]`，人站在上面 `[0.3, 2.1]` → **相切，不相交** → 不推开 ✅
- 墙 `[0, 3]`，人在地上 `[0, 1.8]` → 相交 → 推开 ✅
- 箱子 `[0, 0.6]`，人在箱子里 `[0, 1.8]` → 相交 → 推开 ✅

**"相切不算冲突"这一条同时解决了堆叠问题**（见 §6）。

所以最终形态：

```ts
// 意图集合：过滤过的
const intentSets = blockingRects(state, objectId, fromY, loco);
// 兜底集合：全集（在循环内按 3D 严格相交判定）
const solidSets = setRects(state);
```

## 6. `separateSetAsset` 的 3D 化：相切是堆叠，相交是冲突

`separateSetAsset`（`collision.ts:27-64`）在 `directorStore.ts:898 / 991 / 1086` 被调用 —— **每次拖动 set 资产都会跑**。

**具体 bug**：现在它只判 2D x/z 重叠。所以——

> **你根本无法把一个箱子拖到平台上面。** 箱子的 x/z footprint 与平台重叠 → `separateSetAsset` 立刻把它横向推出去。

**解法**（就是 INV-3D-05，`>` 而非 `≥`）：

```ts
// 只有 [bottom, top] 区间【严格】相交才算冲突
const verticalClash =
  aBottom < bTop - EPS && bBottom < aTop - EPS;   // 严格，不是 >=
if (!verticalClash) continue;                      // 相切 = 堆叠，放行
```

于是：

| 情形 | 垂直关系 | 结果 |
|---|---|---|
| 箱子放在平台上 | `crate.bottom === platform.top` | **相切 → 堆叠，放行** ✅ |
| 箱子插进平台里一半 | `crate.bottom < platform.top < crate.top` | 相交 → 冲突，推开 ✅ |
| 二楼道具与一楼道具 | 区间完全分离 | 放行 ✅ |
| 两个箱子并排 | 区间相交 | 按现有最小穿透轴推开 ✅ |

**这一个 ES 级别的改动，同时修好了"无法堆叠"和"上下层道具互相推"两个问题。**

## 7. `pushOut` / `pushOutAll` 的 3D 化

`routeAround` 在路由前会先把落在障碍里的起终点推出来（`pathfinding.ts:84-85`）。3D 后：

1. **推出后必须重算 `baseY`** —— 否则人悬在半空
2. **推出目标本身要是"可达面"** —— 如果推到的地方 `Δh` 超标，人还是站不住
3. 因此需要**迭代**：推出 → `standable` 检查 → 不通过就继续推（上限 8，与 `separateSetAsset` 的迭代数一致）

## 8. 遮挡的 3D 化

`blockingAssets`（`occlusion.ts:46-50`）现在用 2D `segIntersectsRect`。两处调用：

- `WorldView.tsx:688` → `OcclusionHighlights` 的红色线框 + `BLOCKED` 标签
- `WorldView.tsx:2117` → CameraHud 的遮挡指示

**改造**：

- `segIntersectsRect` → **3D slab test（Liang–Barsky）**，输入机位的 y 与目标的 y（`solveCamera` 的 `resolved.position[1]` / `resolved.target[1]` 已有）
- 收益：**高机位不再被矮墙判遮挡**；**桥下视线不判遮挡**
- **`occluding` 与 `blocking` 拆开**：现在遮挡体与障碍共用 `role === "set"` 同一集合（`occlusion.ts:48, 54`）。3D 后必须拆 —— 否则栅栏会挡住镜头，这在电影语言里是错的（栅栏该看得见对面）

**UI 侧的连带修改**（`WorldView.tsx:705-714`）：

- 线框盒 `position={[b.x, 0, b.z]}` → `[b.x, b.bottom ?? b.baseY, b.z]`（现在是写死 0）
- `BLOCKED` 标签 `position={[0, b.footprint.h + 0.4, 0]}` → `[0, (b.baseY + b.footprint.h) + 0.4, 0]`

## 9. 过滤顺序：可达性 → `canStraddle`

```
setRects（全集）
  → blockingRects（可达性过滤：迈得上 / 跳得过 / 穿得下 / 语义开关）
  → canStraddle 过滤（编队骑得过）
```

顺序不能反。理由：`canStraddle`（`solver.ts:33-48`）问的是"编队横向跨度够不够绕过这个障碍" —— 这个问题的前提是**它本来就是个障碍**。如果它已经因为"迈得上"被排除了，`canStraddle` 再判一次是浪费时间且语义混乱。

**注意**：3D 化后 `canStraddle` 的适用面会**收窄** —— 只有 `Δh > maxJumpHeight` 的高障碍（细高柱、树）才需要它。这是符合预期的：矮障碍现在由"迈上去/跳过去"接管了。**`canStraddle` 函数本身一行不改。**

## 10. 兼容性映射总表

| 现有机制 | 3D 后怎么变 | 改动量 |
|---|---|---|
| `setRects` | 保留不动（= 全集，供兜底用） | **0** |
| 新增 `blockingRects` | 可达性过滤 | 新函数 |
| `routeObstacles` | 改调 `blockingRects` 再 `canStraddle` | **1 行** |
| `groupInfluenceOffset` 的 `sets` | 拆成 `intentSets`（过滤）+ `solidSets`（全集） | 小 |
| `canStraddle` | **不动** | **0** |
| `avoidObstacles` / 可见图 / Dijkstra / `polylineBlocked` | **不动** | **0** |
| `routeAround` 的节点 | **不动**（仍 2D 四角，高度由地面派生） | **0** |
| `pushOut` / `pushOutAll` | 推出后重算 `baseY` + `standable` 迭代 | 小 |
| `separateSetAsset` | 加垂直区间**严格**相交判定 | 小 |
| `footprintsOverlap` | 同上（目前无外部调用方，可顺手一起改） | 小 |
| `blockingAssets` | 2D → 3D slab test；`occluding` 与 `blocking` 拆开 | 小 |
| `routeCache` / `objectRouteCache` | key 加量化的 `fromY` | 小 |
| `OcclusionHighlights` 的盒位置 | 加 `baseY` 偏移 | 2 行 |

**结论：避障的核心算法（可见图、Dijkstra、编队骑过、侧向分流、二次兜底）一行不改。** 改的只是"喂进去的障碍集合"和"垂直方向的相交判定"。

这是本方案最大的兼容优势，来源是一个刻意的设计选择：

> **不给可见图加第三维。** 行走本来就是近似 2D 的，y 由地面派生。一旦给 `pathfinding` 加 z，四角节点就要变 8 节点、`routeAround` 的可见性判定要变 3D、整套绕障重写。

## 11. 回归测试清单

`worldMode: "planar"` 时，以下必须**逐像素 / 逐值一致**：

1. `blockingRects` 的返回 === `setRects` 的返回（因为 `maxStep = 0` 只排除 `top ≤ 0` 的地面板）
2. 现有全部示例场景的渲染截图
3. 现有全部示例场景的导出视频
4. `separateSetAsset` 在 planar 下的拖动结果（垂直判定必须**恒为真**，否则行为会变）
5. 组队动力学：编队保持、变阵、侧向分流（`solver.ts` 的 `canStraddle` 路径）
6. 遮挡判定：`blockingAssets` 的结果集合

入口：`engine/__check.ts`、`engine/headlessApi.ts`。
