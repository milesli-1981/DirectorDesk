# 02 · 跳跃与攀爬

> 本文回答：**跳跃距离怎么设计**、跳跃轨迹怎么表达、攀爬和跳跃怎么区分。
> 核心主张：**跳跃不是一个物理参数，而是一条由两个导演旋钮生成的可行性包络。**

---

## 1. 为什么不用物理引擎

重复一遍理由（详见 [00-总纲 §2 决策 3](./00-总纲.md)）：求解必须是**时间的纯函数**，因为渲染 / 相机解算 / 遮挡 / 景深 / 视频导出 / headless 共用同一份求解，且正反向擦洗必须一致。有状态的刚体积分会摧毁这个不变量。

但物理**公式**可以用 —— 它们只是闭式函数，恰恰是纯函数。所以下面用能量守恒推导，只是把结果固化成公式而不是积分器。

---

## 2. 两个导演旋钮

UI 只暴露两个数（遵循项目既有风格：`STYLE_PRESETS` 注释明写"UI 不暴露原始数值"）：

| 旋钮 | 符号 | human 默认 | 含义 |
|---|---|---|---|
| **跳跃高度** | `H` | `0.9 m` | 原地能跳起的最大高度 |
| **跳远距离** | `R` | `2.5 m` | **平地**能跳出的最远水平距离（助跑跳） |

内部反推（`g = 9.8` 固定，不暴露）：

```
vy0 = sqrt(2·g·H)          起跳竖直初速，使最高点恰为 H
T   = 2·vy0 / g            平地滞空时间（对称抛物线）
vh  = R / T                水平速度
```

**数值验算**（H=0.9, R=2.5）：`vy0 = 4.20 m/s`（≈ 人的起跳速度）、`T = 0.857 s`、`vh = 2.92 m/s`（≈ 10.5 km/h）。物理上完全合理，说明这两个旋钮的默认值选得对。

## 3. 跳跃包络（本文的核心公式）

**问题**：起跳面与落点面有高差 `Δh` 时，最多能跳多远？

从 y=0 起跳、落到 y=Δh，取抛物线的下降支：

```
t(Δh)   = [vy0 + sqrt(vy0² − 2g·Δh)] / g          滞空时间
reach(Δh) = vh · t(Δh)
```

代入 `vy0`、`vh` 化简（`g` 全部约掉）：

```
┌────────────────────────────────────────────┐
│  reach(Δh) = R/2 · ( 1 + sqrt(1 − Δh/H) )   │
└────────────────────────────────────────────┘
```

**只用 `H` 和 `R` 两个数**，`g` 与 `v0` 都消失了。这条曲线就是"跳跃距离怎么设计"的答案。

### 性质（都可验证）

| `Δh` | `reach` | 解读 |
|---|---|---|
| `0` | `R/2·(1+1) = R` | 平地基准 ✅ |
| `+H`（跳到最高点） | `R/2·(1+0) = R/2` | 跳到极限高度时，水平还剩一半 ✅ |
| `−H`（往下跳一个身位高度） | `R/2·(1+√2) ≈ 1.21 R` | **落差越大摔得越远** ✅ 符合直觉 |
| `>H` | 根号内为负 → **不可达** ✅ |

**单调递减、上凸**，`Δh → −∞` 时 `reach → ∞`（无限落差当然能跳无限远，现实中受限于"落地面"）。

### UI 上的表达

这条曲线应当直接画给导演看（Δh 横轴 / reach 纵轴 / 一条单调下降的曲线），并把当前路径的 `(Δh, dx)` 作为一个点标在上面：

- 点在曲线**下方** → 跳得过去 → 「需跳跃」，可一键生成弧线
- 点在曲线**上方** → 「跨度太远，跳不过去」

这比给一串数字直观得多，而且**把"能不能过"变成了一眼可见的几何关系**。

## 4. 弧线本身：apex 由作者定，可达性由包络校验

这是本方案与"真物理"最重要的分歧点。

**不做**：给定 `vy0` 和 `vh` 自动算出轨迹（物理正确，但导演无法控制"跳多高"）。
**要做**：把**顶点高度 `apex` 作为作者旋钮**（UI 上直接拖弧线顶点），系统只做可行性校验。

```ts
interface VerticalArc {
  mode: "parabola" | "fall" | "climb";
  from?: number;      // 归一化里程
  to?: number;
  apex?: number;      // 顶点相对"起跳点地面"的高度，作者拖拽设定
  climbSeconds?: number;
}
```

轨迹（纯函数，与水平速度解耦）：

```
s    = (u − from) / (to − from)          u = 路径归一化里程
y(u) = groundAtStart + apex · 4·s·(1−s)   标准抛物线，s=0.5 处达顶点
```

**校验三条（任一失败即报错，而不是默默画出来）**：

| 校验 | 条件 | 失败文案 |
|---|---|---|
| 顶点够高 | `apex ≥ Δh` | 「弧顶低于落点，跳不上去」→ **自动抬到 `Δh`** |
| 顶点不超能力 | `apex ≤ H` | 「超过跳跃高度上限」 |
| 跨度在包络内 | `dx ≤ reach(Δh)` | 「跨度太远，跳不过去」 |

**与水平速度解耦的好处**：路径的水平速度曲线（`ease` / `speedKeys`，`schema.ts:47-52`）**不需要为跳跃做任何改动**，跳跃自动跟着路径走向走。这是"垂直三级权威"的直接收益。

### `fall` 与 `climb` 两种模式

| mode | 垂直曲线 | 用途 |
|---|---|---|
| `parabola` | `apex · 4s(1−s)` | 跳上、跳过 |
| `fall` | `(y1 − y0) · s²`（加速下坠） | 落差下落（`Δh < −maxStep`） |
| `climb` | 分段：先水平靠近 → 竖直上移 → 水平落到面（贴墙） | 攀爬 |

`fall` 用 `s²` 而不是线性：线性会看起来像"电梯下坠"，`s²` 才有重力加速感，而且它同样是 `s` 的闭式函数，保持纯函数性质。

## 5. 助跑：一个必须处理的既有陷阱，而且它同时也是正确答案

**陷阱**：默认的 cubic-bezier 缓动在 `u = 0` 处**斜率为 0**（`ease.ts`）。而跳跃的 `from` 通常就落在段起点附近 —— 结果是**水平速度为零，人在原地弹起、原地落下**，看起来完全不像跳跃。

这不是新问题，是"缓动端点零速"这个既有特性在垂直维度上的暴露。它已有的痕迹在 `solver.ts:598-500` 的注释里（"默认缓动在 u=0/u=1 斜率为 0，waypoint 附近 anchor 必有一段近零速区间"）。

**三层解法**：

1. **跳跃段内强制准线性水平速度**：在 `[from, to]` 区间覆盖 `ease`，用接近线性（如 `[0.15, 0.15, 0.85, 0.85]`）的曲线，保证起跳瞬间有水平速度。
2. **检查起跳点的瞬时速度**（`solver.ts` 已有求速度的差分代码可用）。若 `speed < 0.6 · vh` → **报"起跳前没有助跑"**，并提示在跳跃前留出助跑距离。
3. **有效跳远随实际速度缩放**：

```
speedRatio    = clamp(实际起跳水平速度 / 跑步速度, 0, 1)
reachEffective = R · mix(0.5, 1.0, speedRatio)
```

即：**站着跳只能跳到一半远，跑起来才是 `R`。** 这既是真实感，也把"助跑"这个导演语言变成了可感知的参数 —— 想让人跳得更远？在跳跃前加一段助跑。

> 第 3 条让"助跑"从一个 bug 变成了一个**可调的表达手段**。这是设计上最划算的一笔。

## 6. 起跳点 / 落地点的提前量

**真实 bug**（3D 游戏里非常常见）：如果 `from` 恰好等于起跳面的边缘里程，人会**先踏空再起跳** —— 脚在面外、身体才开始上升，看起来像"从悬崖上掉起来"。

**规则**：

- 起跳点 `from` 应**早于**起跳面边缘 `pb = 提前量 / 总里程`（默认提前 0.25 m）
- 落点 `to` 应**晚于**落点面边缘（默认延后 0.25 m）—— 人落地后需要迈一步站稳，而不是脚尖点一下就停

**默认值由几何自动求解**（起跳面与落点面的边缘里程可以从 `groundHeightAt` 沿路径扫描得到），允许手动微调。UI 上把这两个偏移点画成两个小把手。

## 7. 落地校验

跳跃轨迹画出来之后，必须再验两件事：

### a. 轨迹不与几何相交

沿弧线采样（固定步长 0.1 m），检查每个采样点 `(x(u), y(u), z(u))` 是否落在任何对象的 `[bottom, top]` 与 `(x,z)` footprint 之内。**第一次相交**即为撞点：

> 「跳跃轨迹撞到「石墙」，请抬高弧顶或改变落点」

这能捕捉"跳过一堵比 `apex` 还高的墙"这类错误。

### b. 落点必须站得住

`standable(落点, fromY = 弧顶高度, loco)` 必须 `ok`。否则：

> 「落点站不住：落差 2.6 米超过攀爬能力」

**落地高度 = 落点 `groundHeightAt`**，不允许"落进台阶里"。

## 8. 攀爬与跳跃的区分

| | **跳跃 Jump** | **攀爬 Climb** |
|---|---|---|
| 高度范围 | `maxStep < Δh ≤ maxJumpHeight` | `maxJumpHeight < Δh ≤ maxClimbHeight` |
| 前提 | 水平跨度在包络内 | 落点边缘存在**竖直抓手面** |
| 轨迹 | 抛物线（离地） | L 形贴墙：水平靠近 → 竖直上移 → 水平落到面上 |
| 时长 | 由 `apex` 与包络推算 | 由攀爬速度推算（默认 `1.2 m/s`） |
| 姿态 | 起跳 / 滞空 / 落地 | 举手抓握 / 引体 / 跨上 |
| 弧线形状 | 弓形 | 折线（贴墙） |

### 抓手判定：因为一切都是盒子，它是免费的

**关键洞察**：我们所有的几何都是**盒**（`bottom` 到 `top`），而**盒的侧面永远是竖直面**。所以"有没有抓手"不需要单独的几何检测 —— 只要落点面的支撑体是一个盒，它天然自带竖直抓手面。

判定条件退化为简单的三条：

1. 落点面的**顶面**高于起点面：`Δh > 0`
2. 高差在能力内：`Δh ≤ maxClimbHeight`
3. 水平距离 ≤ **一个身位**（默认 0.5 m，即人贴着这个面）

> 唯一的例外是 `ramp` 与 `grid`（它们的侧面不是竖直面）。这两个形态**不提供抓手** → 无法攀爬，只能跳。

## 9. 能力表：阈值挂在**运动主体**上，不是障碍上

这是"所有 case 考虑详细"必须补的一个维度 —— **同一堵台阶，人上得去、车上去、马跳得更高。**

```ts
// engine/locomotion.ts
export interface Locomotion {
  /** 单步最大落差（可自动迈上）。 */
  maxStep: number;
  /** 最大可行走坡度（度）。 */
  maxSlopeDeg: number;
  /** 原地起跳高度。0 = 不会跳。 */
  maxJumpHeight: number;
  /** 平地助跑跳远。 */
  maxJumpReach: number;
  /** 最大攀爬高度。0 = 不会攀爬。 */
  maxClimbHeight: number;
  /** 身高（净空判定用）。 */
  height: number;
  /** 脚底宽度 / 深度（落脚采样用）。 */
  foot: { w: number; d: number };
}

export const LOCOMOTION: Record<AssetCategory, Locomotion> = {
  human:   { maxStep: 0.35, maxSlopeDeg: 45, maxJumpHeight: 0.9, maxJumpReach: 2.5,
             maxClimbHeight: 1.6, height: 1.8, foot: { w: 0.6, d: 0.6 } },
  animal:  { maxStep: 0.5,  maxSlopeDeg: 40, maxJumpHeight: 1.2, maxJumpReach: 3.5,
             maxClimbHeight: 0,   height: 1.1, foot: { w: 0.9, d: 1.6 } },
  vehicle: { maxStep: 0.15, maxSlopeDeg: 20, maxJumpHeight: 0,   maxJumpReach: 0,
             maxClimbHeight: 0,   height: 1.5, foot: { w: 2.0, d: 4.2 } },
};
```

**`DirectorState.locomotion` 允许按场景 override** 单类别：

```ts
locomotion?: Partial<Record<AssetCategory, Partial<Locomotion>>>;
```

这样"骑马的人"（人类但能跳 1.2m）或"受伤的人"（`maxStep: 0.2`）都能表达，而不用新增资产类别。

**planar 世界 = 能力表退化**：`maxStep: 0`、`maxJumpHeight: 0`、`maxClimbHeight: 0`、`worldMode: "planar"`。此时所有 set 资产（建筑 top=24、桌子 top=0.9）都保留为障碍 —— **与现状逐像素一致**。详见 [00-总纲 §4](./00-总纲.md)。

## 10. 组队跳：天然工作，不需要额外代码

编队是**路径弧长参数化**的（`solver.ts:335-343`：队员取 `s = s_anchor + slot.fwd`，沿路径采样）。所以锚点需要跳时，每个队员**各自在自己的弧长处**跳同一段弧线 —— 一队 5 人会在弧线上排成一列依次跳过，正是想要的效果。

**唯一要做的**：徽标只画在锚点段的弧上，避免一队 5 个人 5 个徽标。

## 11. 明确的局限（要说清楚，别让导演踩坑）

**跳跃只能沿路径方向。** 因为路径是 2D 的、y 由弧线派生，所以**不能横向跳**（"往左前方跳上侧面的平台"）。

这不是缺陷 —— 在这个模型里它表现为：**路径先拐向目标，再在那一段上加弧线**。也就是说横向跳 = 两段路径 + 一段弧线，是可达的，只是需要多画一个路点。

如果将来确实需要自由 3D 跳跃，那就要给 `PathPoint` 显式 `y` 并且放弃"路径 2D + 垂直派生"这个简化 —— 代价是整个 `pathfinding.ts` 要重写。**不值得，先不做。**

## 13. Phase 4 落地后的已知边界

- **弧线只沿路径方向**：横向跳仍要靠"两段路径 + 一段弧线"（见 §11）。
- **`reach` 取路径全程的保守判断**：一段内从低处爬到高处时，低处的分类会让它绕开本可越过的
  低障碍（`avoidance.ts` 的 `routeHeightFor` 取 MIN）。这是保守方向的误差，v1 接受。
- **起跳瞬时速度**：✅ **Phase 5 已接线** —— `engine/reach.ts` 的 `takeoffSpeedRatio`
  给出 `d(弧长)/dt ÷ RUN_SPEED`（时间的纯函数），Inspector 的弧线校验据此缩放有效跳远
  并决定是否报"没有助跑"。折线取求解器真正走的那条（绕障会拉长路程 ⇒ 同样的时间走完就更快）。
  `RUN_SPEED = 1.6` 是 `locomotion.ts` 里的唯一常数，与步态判定共用。
  **不要用 `ease.ts` 的 `curveSpeed` 取这个速度**：它在 `u = 0` 处用固定中心差分，
  而 `u − h` 被夹回 0 ⇒ 端点斜率被系统性少算一半，而"起跳点常在段首"正是这里的常态。
- **`standingAt` 只看落点面**：不做"落点能否摆开身位"的拓扑检查（盒足够大时才相关）。
