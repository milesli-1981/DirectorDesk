## 0. 一句话结论

现在不是"3D 但很平"，而是**整个创作层与求解层共享同一个断言**：

> 地面恒为平面 `y = 0`，且"位置"就等于 `(x, z)`。

**但体积模型其实已经在数据里了。** `Footprint = { w, d, h }`（`schema.ts:29`），`role: "set"` 的定义就是"静态环境（遮挡 + 障碍）"（`schema.ts:25`），渲染时它确实被画成了一个从 `[0, h]` 的实心盒（`WorldView.tsx:331-332`）。

所以：

> **不需要新造一套地形系统。对象就是几何。**
> 只是三个地方把已有的体积扔掉了，补上即可。

1. **没有 `baseY`** —— 盒子永远从 0 起，所以堆不起来
2. **`occlusion.ts` / `collision.ts` 只读 `x / z`** —— `h` 被无视（矮墙挡高机位、上下层道具互相推）
3. **没有"我站在谁上面"的查询** —— 地面恒等于 0

补上之后，**台阶 / 高低差 / 堆叠 / 跳跃 / 桥下穿行全部由一条规则涌现**，不需要各自特判。

一个有利事实：相机路径点 `CameraPathPoint` **已经带 y**（`schema.ts:131-138`）—— 相机那半边早就是 3D，只有演员是 2D。

## 2. 五条核心决策

### 决策 1 · 一切静态几何都是 `DirectorObject`

台阶、平台、墙、桌子、桥、丘陵 —— 全都是对象，都进同一个列表，复用同一套拖拽 / Inspector / 锁定 / 隐藏 / 持久化机制。

- **盒子**：`baseY` 与 `footprint.h` 定义它占据 `[baseY, baseY + h]`
- **`h` 的语义升级**：从"视觉高度"升级为**实体范围**。全篇唯一一处真正的语义破坏（见 §6 风险）
- 形态扩展：`bottom`（拱桥）、`topShape: "ramp"`（坡道）、`grid`（丘陵）、`array`（楼梯，Phase 7）

> 没有"台阶算地形还是算对象"这个问题了 —— 它永远是对象。

### 决策 2 · 地形只是一个"特殊对象"

起伏地形无法用少量盒子表达，但**它可以是一个对象**：`category: "terrain"` + `grid` 高度场。照样出现在列表里、可隐藏 / 锁定 / 整体移动，只是顶面不是平面。求解侧对它的处理只是"多一个采样分支"。

### 决策 3 · 不引入物理引擎；垂直运动是"作者化的时间函数"

**最重要的一条**，尊重现有代码最强的那个不变量：

> 求解是「时间的纯函数」—— 正反向擦洗一致、可按 `revision` 缓存、渲染 / 相机解算 / 遮挡 / 景深 / 视频导出 / headless 共用同一份求解。

`objectPosition(state, id, time)` 这个签名就是载体。刚体物理有状态、倒放不回到同一结果；而求解每帧调用极频繁（含组动力学的 11 次低通重采样，`solver.ts:517-548`）。

- **贴地**是派生的：`y = 可落脚面的顶面高度`
- **跳跃 / 落差 / 攀爬**是作者化的：显式弧线，仍是 `time` 的函数
- 只有导演不控制的程序化小道具（碎石、落叶）才允许用物理，且不进主求解链

### 决策 4 · 路径仍是 2D `(x, z)` + 可选钉高

把 y 烘进路径会丢掉"在地面拖拽"这个最顺手的交互，地形一改所有路径高度全废，2D 可见图寻路也会整体报废。

规则：**路径决定 x/z 与朝向，几何决定 y，除非 `PathPoint.y` 显式钉高。**

### 决策 5 · 世界模式有"场景级"和"手势级"两层

`worldMode` 是**场景级**的：持久、全局、决定整个世界的解算方式。但作者的真实诉求常常是局部的
——「我只想把这一摞盒子叠起来，然后接着画平面图」。为此补一层**手势级**覆盖：

> **拖拽 / 拖放时按住 Shift = 这一次操作按 terrain 语义走。**

覆盖只作用在**落点拾取**（`raycastGround`）与**落位吸附**（`placeObject`）两处，
不写回 `state.worldMode`。

**为什么不直接把覆盖写回 `worldMode`**：它是能力表的总闸（`locomotion.ts` 看到 `planar`
会把整个能力表换成 `PLANAR_LOCOMOTION`），改它就等于全场景重解算 —— 场内所有演员会瞬间跳到
台阶上、路径标记整体抬升、高度手柄凭空出现，松手又全部退回。一个按键引发全场跳变，
噪音远大于收益，还会把「把这一个盒子放上去」和「我要看 3D 世界」两件事混在一起。

**为什么覆盖只改两处就够**：一旦 `baseY` 写进数据，渲染 / 站立 / 路径贴地这些**稳态**行为
本来就读 `baseY`（`standingHeightFor` / `pathGroundAt`），而 planar 的 `maxStep = 0`
恰好等于「只在自己那一层里走动」。所以松开 Shift 之后一切照旧正确，**不需要任何额外的模式判断**
—— 这正是决策 3「几何决定 y」的延伸：高度是数据，不是模式。

实现落在 `engine/worldMode.ts` 的 `effectiveState(state, forceTerrain)`：返回一份
「世界模式 = terrain」的 state 视图，已有 terrain 时原样返回同一引用（零分配，且让
`ground.ts` 的桶索引缓存稳稳命中）。Shift 状态由画布从指针 / 拖放事件上直接读
（`event.shiftKey`），**不装全局键盘监听** —— 那样会在 Inspector 输入框里打大写字母时误触发。

## 3. 数据模型

```ts
// domain/schema.ts

export type WorldMode = "planar" | "terrain";
export type TopShape = "flat" | "ramp";

/** 规则网格高度场：双线性采样，O(1)。 */
export interface GridHeight {
  cols: number; rows: number; cell: number;
  /** 网格左上角世界坐标。 */
  ox: number; oz: number;
  /** 行优先，长度 = cols * rows。 */
  data: number[];
}

/** 阵列：一个对象展开成 N 个盒，避免 20 级台阶在列表里占 20 行。 */
export interface BoxArray {
  count: number;
  /** 每个副本的相对位移（沿局部轴）。 */
  stepX: number; stepY: number; stepZ: number;
}

export interface DirectorObject {
  // 已有：x, z, rotation, footprint{w,d,h}, category, role, color, ...

  // ── 新增 · 几何 ──
  /** 底面高度（世界米）。默认 0。堆叠 = 上层取"下方顶面"。 */
  baseY?: number;
  /** 实体底面，低于 baseY 时即"拱洞 / 桥"。默认 = baseY。
   *  例：桥面 baseY=2.75, bottom=2.4 → 下方留 2.4m 净空。 */
  bottom?: number;
  /** 顶面形状，默认 "flat"。ramp = 沿局部 +Z 从 bottom 升到 top。 */
  topShape?: TopShape;
  /** 阵列展开。 */
  array?: BoxArray;
  /** 仅 category === "terrain"：用高度场取代平面顶面。 */
  grid?: GridHeight;

  // ── 新增 · 语义开关（默认全自动推导，仅在需要时 override）──
  /** 可站上去。默认由 maxStep 推导。水面 / 沼泽设 false。 */
  walkable?: boolean;
  /** 水平阻挡。默认 true。栅栏 / 草丛可设 false。 */
  blocking?: boolean;
  /** 遮挡相机视线。默认 true。玻璃可设 false。 */
  occluding?: boolean;
  /** 倾向绕行而非跳跃（刺丛、水坑）。默认跳过。 */
  prefer?: "jump" | "walk-around";
}

/** 堆叠关系：与 Handoff 同构。坐标存绝对值（single source），关系只记连接。 */
export interface Support {
  id: string;
  upper: string;
  /** null = 直接落在基准面上。 */
  lower: string | null;
}

/** 垂直弧线：跳跃 / 跨越 / 落差 / 攀爬。挂在 MoveSegment 上，不新增时间轴轨道。 */
export interface VerticalArc {
  mode: "parabola" | "fall" | "climb";
  /** 在路径归一化里程中的起止（0..1）。省略 = 全程。 */
  from?: number;
  to?: number;
  /** parabola：顶点相对"起跳点地面"的高度（米）。由作者拖拽设定。 */
  apex?: number;
  /** climb：攀爬耗时（秒）；省略则按 1.2 m/s 与落差推算。 */
  climbSeconds?: number;
}

export interface PathPoint { y?: number; }
export interface MoveSegment { vertical?: VerticalArc; }

export interface DirectorState {
  /** 缺省 "planar"，老场景行为不变。 */
  worldMode?: WorldMode;
  supports?: Support[];
  /** 能力表 override（缺省走 engine/locomotion.ts 的按类别预设）。 */
  locomotion?: Partial<Record<AssetCategory, Partial<Locomotion>>>;
}
```

### 堆叠怎么存：绝对值 + 关系记录

沿用 `Handoff` 已确立的模式（`schema.ts:163-173` 原话："坐标本身仍由两条 leg 各自保存（single source 通过 store 同步保证），Handoff 只记录连接关系与模式"）：

- **存储：绝对 `baseY`** → 求解是纯函数、无环风险、可缓存
- **关系：`Support { upper, lower }`** → 记录堆叠链路
- **编辑时**：拖堆叠根，store 传播移动整塔（就像 `reconcileHandoffs` 重算关系）。**求解器永远看不到 `Support`**

存相对偏移会引入环（A 在 B 上、B 在 A 上），求解器必须处理它 —— 不值得。

### 迁移

挂载点已有：`directorStore.ts:611` 的 `sanitizeState()`。补 `worldMode ?? "planar"`、`supports ?? []` 即可。

## 4. 一条统一规则（全文的支点）

```ts
// engine/ground.ts
export function groundHeightAt(
  state: DirectorState,
  x: number, z: number,
  /** 查询起点高度（通常是该对象当前 y）。只考虑"够得着"的面。 */
  fromY: number,
  /** 单步最大落差（米）。 */
  maxStep: number,
): number
```

> 在所有覆盖 `(x, z)` 的静态对象中，取**顶面 ≤ `fromY + maxStep`** 的那些，返回其中最高的顶面；一个都没有 → `0`（基准面）。

| 需求 | 如何涌现 |
|---|---|
| **台阶** | 0.3m 的盒，`0.3 ≤ 0 + 0.35` → 可达 → 走上去。**零特判** |
| **高低差** | 3m 的盒，`3 > 0.35` → 不可达 → 留在地面；同时仍被水平障碍测试挡住 → 绕行 |
| **堆叠** | 箱子 B：`B.baseY = A.top` → B 的顶面 = `A.top + B.h` |
| **桥下穿行** | `bottom = 2.4` > 人高 → 障碍测试放行 |
| **跳跃** | 站 3m 平台上时 `fromY = 3`，该盒变可达；走出边缘 → 目标面变 0，落差 3 > 0.35 → 必须由弧线补 |

**"我在几层"由 `fromY` 上限解决。** `h=24` 的实心建筑从地面查询时顶面不可达 → 人不会跑到屋顶；从屋顶查询时才可达。这就是标准角色控制器的 step up / step down 查询。

### 垂直三级权威

① **显式钉高**（`PathPoint.y` / `baseY`）> ② **弧线**（jump / fall / climb）> ③ **几何派生 `groundHeightAt`**

**平面世界 = 这三级全部退化**：`worldMode: "planar"` 等价于 `maxStep = 0` + 无跳跃 + 无攀爬。因为 `top ≤ 0 + 0` 只有地面板够格，建筑（top 24）、桌子（top 0.9）全部保留为障碍 —— 与现状完全一致。

> **planar 不是特例分支，而是能力表的退化取值。** 这条让整个改造不需要任何 `if (planar)` 特判。

## 5. 性能与缓存

`groundHeightAt` 每帧调用次数：求解 ×2/演员 + 相机解算（含防抖时间窗口重采样）+ 遮挡 + 景深 + 组动力学的 11 次低通重采样。

**静态几何是静态的**：按 `state.revision` 建一次均匀网格桶索引（bucket grid），把 `(x,z)` 映射到覆盖它的对象列表。写法复用现有缓存范式（`path.ts:113 routeCache`、`solver.ts:205 objectRouteCache`）。

**硬约束**：
1. `groundHeightAt` 纯函数、无状态、零分配
2. 渲染侧网格与 CPU 采样必须来自同一份数据
3. **求解器绝不读渲染网格、绝不用 `three.Raycaster`**（headless 与缓存都依赖它是纯 CPU 纯函数）

> 缓存 key 在 3D 下会有一个陷阱（`blockingRects` 依赖 `fromY`，而 `fromY` 随时间变）—— 详见 [04-避障兼容.md §4](./04-避障兼容.md#4-缓存-key-的陷阱必须解决)。

## 7. 风险与回归保护

| 风险 | 说明 | 保护 |
|---|---|---|
| **`h` 语义升级是破坏性的** | `h` 从"视觉高度"变"实体范围"后现有场景遮挡/碰撞结果会变（树 h=4 现在会挡 1.7m 机位 —— 更对，但是变化） | `worldMode: "planar"` 短路；每 Phase 截图 + 导出视频对比 |
| **`fromY` 让缓存爆炸** | `blockingRects` 依赖随时间变化的 `fromY` | 按段起点 y 分类 + key 量化（见 04 §4） |
| **`rotation` 被碰撞/遮挡完全忽略** | 现有隐藏 bug：把 10×1 的墙转 90°，视觉转了但障碍还是原 AABB | 限制 set 资产 yaw ∈ {0,90,180,270}（AABB 仍精确）；详见 01 §4 |
| **走台阶会因为 y 突变而抖** | 10cm 台阶让身体和相机抖 | y 时间低通，复用 `solver.ts:517-548` 的写法 |
| **跳跃起跳点速度为零** | 默认 cubic-bezier 在 u=0 斜率 0 → 原地弹起原地落下 | 强制跳跃段线性水平速度 + 助跑校验（见 02 §4） |
| 寻路节点爆炸 | 每盒加 8 节点（四角 × 上下）图会变大 | 节点只留 2D 四角，高度做成边的可行性条件 |
| 对象列表污染 | 台阶/墙会出现在相机目标下拉、组队成员、时间轴 | 按 `role`/`category` 过滤 UI 候选；列表分组折叠 |
| 老场景回归 | 高度体系改错会让所有现有场景错位 | planar 短路 + `__check.ts` / `headlessApi.ts` 作回归入口 |

## 8. 明确不要做

1. **不要引入刚体物理引擎**（cannon / rapier）。摧毁"求解是时间的纯函数"，而相机解算、遮挡、景深、导出、headless 全建在它上面。
2. **不要做真正的 CSG 镂空 / 布尔**。`bottom` 就能表达"拱洞 / 桥"这个 90% 场景；布尔带来巨大几何复杂度而收益有限。
3. **不要把 y 烘进路径作为主表示**。地形一改所有路径失效，且丢掉"在地面上拖拽"这个最顺手的交互。
4. **不要给可见图加第三维**。行走本来就是近似 2D 的，y 由地面派生 —— 保持 `pathfinding.ts` 完全不变是本方案最大的兼容优势。

### 9.3 落地时发现并修掉的 bug 与两个关键决策

**① `separateSetAsset` 只判 2D 重叠 → 盒子永远叠不起来。**
把盒子拖到平台正上方，会被水平推开。修法：加 `verticalOverlap`（**严格** `<`，
留 `1e-6` 容差让"相切"稳定判为不相交），分离循环里跳过垂直不相交的对。
> 这条同时修掉了一个扩展前就存在的现象：把道具拖到平台**上面**会被弹开。

> ⚠️ **这条修得不完整**，见下面 ④ —— 改对了判定，但**调用顺序**还是错的，
> 所以上面那个现象在真机操作里依然存在。§3 的用例之所以一直是绿的，
> 是因为它在调用 `separateSetAsset` 前就把 `baseY` 预设好了（= 只测了函数，没测流程）。

**② 桶索引用 `revision` 做 key 是错的。**
`revision` 只在单场景内单调，**跨场景不唯一** —— 切场景页 / 撤销重做 / 导入一份
`revision` 相同的存档，会让另一份几何命中同一份旧缓存，地面高度**静默算错**。
修法：key 改为 `objects` 数组引用（store 每次改动都产新数组，判断成本为 0）。
`worldMode` 因为不换 `objects` 数组（`{...state, worldMode}`）必须单独进 key。

**③ 桶索引按"未旋转的 footprint"分桶，不是旋转矩形的超集。**
原先想当然地认为"轴对齐外接盒覆盖旋转矩形"，于是分桶直接用 `footprint.w/d`。
错在：旋转后的矩形在两个轴上都可能超出原 footprint。把 10×1 的墙转 90° 后它实际铺在
`z ∈ [-5, 5]`，而按原 footprint 分桶只覆盖 `z ∈ [-0.5, 0.5]` —— 查询后半截查不到对象，
表现是**"墙转过之后人能从它中间穿过去"**。
修法：新增 `objectHalfExtents()`（标准 OBB→AABB：`hx = |w/2·cosθ| + |d/2·sinθ|`），
分桶与包围范围都用它。§11 有用例。

**④ 「先分离、后定高」的顺序错误 —— 盒子依然叠不上去（真机操作层面）。**
接 ①：`verticalOverlap` 修对了，但三条摆放路径（`moveObject` / `addAsset` / `updateAsset`）
都把 `separateSetAsset` 放在**定 `baseY` 之前**。于是正在抬升的盒子拿的是**旧 `baseY`（= 0）**，
与平台同层 → 垂直必然相交 → 刚拖到平台正上方就被沿最小穿透轴推到旁边。
`stackSnapBaseY` 那一步算出来的高度是**对的**，只是**用得太晚**，算完已经没用了。

```
拖到平台上方           期望              实际（旧顺序）
    ┌──┐                                     ┌──┐
    │D │  ─────►       叠上去                │D │     ┌────┐
    └──┘                ┌──┐                 └──┘     │ D  │ ← 被推到旁边
                        │D │                          └────┘
    ┌────┐              └──┘              ┌────┐
    │ P  │              ┌────┐            │ P  │
    └────┘              │ P  │            └────┘
                        └────┘
```

修法：把「定层高 → 按该层高分离」这**一回事**收敛成 `engine/place.ts` 的 `placeObject()`，
三条路径统一走它。关键一步是用**带上新 `baseY` 的探针数组**去跑分离：

```ts
const baseY = restingBaseY(s, x, z, id, layerY);            // ① 先定高
const probe = s.objects.map(o => o.id === id ? { ...o, baseY } : o);
const sep = separateSetAsset(probe, id, x, z);              // ② 再按该层高分离
```

相切（`baseY == 平台顶面`）稳定判为不相交 → 分离跳过它 → 盒子留在平台上。
`baseY === undefined`（非 terrain）时**原样走旧路径**，planar 逐像素不变。

> 教训：这个不变量**被抄了三份**，于是三份一起错。现在只有一处，且 §13 有正反两面的用例
> （反证那两条断言故意保留旧顺序，让回归测试能解释自己为什么存在）。

**⑤ 拾取把"正在被拖动的对象自己"算进去了 → 自激振荡（真机表现：疯狂抖动）。**

这条是加完 Shift 之后被反馈出来的 —— 用户描述是「物体在检测重叠时会疯狂抖动，放不上去」，
并推测是「Shift 和 3D 按钮之间状态不同步」。**不是状态不同步**：两者根本不共享状态
（手势级覆盖从不写回 `worldMode`，见决策 5）。真正的原因是拾取的**候选集**有自指：

`raycastGround` 的候选 = 基准面 + 所有 `set` 对象的顶面，**没有排除正在被拖的那一个**。
而拖拽的语义就是"物体跟着指针走" ⇒ 指针**永远压在它自己身上** ⇒ 每帧拾到的是
**它自己的顶面** ⇒ `baseY = 自己的顶面 = baseY + h`，每帧把自己的身高再加一遍：

```
俯视相机（射线⊥顶面）       斜视相机（抬高 h/tan俯角 后水平漂出自己）
  f0 baseY=1  ← 拾到「自己」    f0 baseY=1  ← 拾到「自己」
  f1 baseY=2                    f1 baseY=0  ← 漂出去了，落回地面
  f2 baseY=3                    f2 baseY=1  ← 又落回来，再拾到自己
  …  → 一路飞出画布             …  → 1→0→1→0 每帧翻转 = 「疯狂抖动」
```

> ⚠️ **这不是 Shift 的锅。** 只要被拖的对象参与拾取，terrain 模式（3D 开关打开）下的
> 普通拖拽、以及拖入新资产，犯的都是同一个错 —— §15 里两种模式各测一遍，就是为了钉死这一点。
> Shift 只是让 planar 世界**第一次有了"把自己抬高"的可能**，于是把这个潜伏的错误暴露了出来。
> 换句话说：这个 bug 早就在，只是原来 planar 下拾取恒返回 0，抬高无从发生。

顺带还有一处同源问题：被拖的对象还参与**遮挡**判定，会把它身后的一切判成"看不见的"。

修法：`raycastGround` / `layerAtPointer` 增加 `excludeIds: ReadonlySet<string>`，
在**候选**与**遮挡**两个循环里都跳过；画布侧 `dragTarget` 把"本次手势会动的对象"整份传下去。
**用集合而不是单个 id**：团队拖拽时整队一起动，任一队员都可能是指针身下那一块。
（`DragState.object` 因此多了 `movers` 字段，按下时建一次、拖动中复用，不产生每帧分配。）

排除之后，"指针下面的面"才是真正该落脚的那一层 —— 这也正是"能叠上去"的**另一半**条件：

| 指针位置 | 排除自己后拾到 | `baseY` 写入 | 结果 |
|---|---|---|---|
| 盒子悬在平台上方 | 平台顶面 1 | 1 | 叠上去，且此后每帧恒为 1（收敛） |
| 盒子悬在地面上方 | 基准面 0 | 0 | 老实待在地面 |
| 盒子已叠在平台上（顶面 2） | 平台顶面 1 | 1 | **回到 1 而不是涨到 2** ⇒ 停住 |

#### 决策 A · 拖拽：面拾取 + 跨层重锚

「`raycastGround` 替代 `groundPoint`」这条一句话方案直接做会**砸掉拖拽手感**，必须补一步：

- 面拾取给的是**正确的高度**（指着平台就能放到平台上，这是低机位下唯一可行的方式 ——
  只投 `y=0` 时平面投影落在平台**后面**的地上，落点反查得到 0）。
- 但面拾取的水平坐标**在棱边处会跳** `h / tan(俯角)`：从地面跨到 3m 平台顶面时，
  30° 俯角下瞬移 5.2m。直接拿它当拖拽目标，物体越过棱边的那一帧会飞出去。

解法：在**层发生变化的那一帧**把拖拽起点重锚一次，把跳变量吸收进 `origin`：

```
origin += (新落点 − 上一帧落点)      // 仅在 layer 变化时
```

于是物体在跨层瞬间位置连续（等价于"换了一层继续跟手"），此后在新面上正常跟随。
planar 下 `raycastGround` 只返回基准面、layer 恒为同一个值 ⇒ **重锚分支永不触发**，
拖拽与扩展前逐帧一致。

#### 决策 B · 路径与标记的贴地必须"渲染 = 拾取"同源

原地形一进来，路径标记的"浮空量"从常量变成了随地面变化的量。渲染与拾取若各写各的高度，
就会出现**"屏幕上看在那里、却怎么都点不中"** —— 这正是旧代码 `POINT_MARKER_Y` 注释记录过的坑，
只是原因从"固定容差遇上浮空标记"变成了"两边算的浮空量不同"。
所以全部收敛到 `pathGroundAt(state, objectId, x, z) + LIFT` 一处（`ground.ts`），
渲染与 `hitPathPointScreen` / `hitEndpointScreen` 都调它。

另外，每个标记只订阅**自己那一个高度数字**（`useDirectorStore((s) => pathGroundAt(...))`）
而不是整个 `state`，避免播放时每帧重渲染一批 DOM 按钮。

10. 这样垫高的盒子**仍然可以在平面模式下微调**：选中它，高度手柄照样出现
    （出现条件是「3D 开着」**或**「这个对象已经有标高」）。
11. 覆盖**不会**改变演员的运动学：平面模式下按住 Shift 不会让场上演员跳到台阶上
    （`locomotionOf` 始终没被覆盖碰到）。要改运动学仍然得开 3D 开关。
12. **按住 Shift 拖入一个「团队」**：弹出的配置面板照常出现在落点上；点「创建团队」后，

### 9.6 自激振荡这个 bug 的教训

三个层次都值得记一笔：

1. **数值复现比断言值钱。** §15 不是"断言某个函数返回什么"，而是把
   「每帧拾取 → 落位 → 写回」这个**循环**跑 8 帧，看高度序列收不收敛 ——
   这个循环在真机上就是 `handleMove`。8 帧跑出 `1,2,3,…,8` 的那一瞬间，
   原因就自己浮出来了，不用猜。凡是"状态在闭环里自己喂自己"的 bug，都该这么测。
2. **用户的归因经常是错的，但症状描述是准的。** "疯狂抖动""放不上去"精确到可以直接翻译成
   `1→0→1→0` 的翻转；而"Shift 和 3D 按钮状态不同步"这个猜测是错的 ——
   两者不共享任何状态。**信症状，自己找机理。**
3. **新功能常常只是旧 bug 的显影剂。** 这个错误在 Shift 之前就存在（terrain 模式同样中招），
   只是 planar 下拾取恒返回 0、抬高无从发生，所以没人看见。加功能时顺手怀疑一下
   "我是不是只是把它照出来了"，往往能省掉一次归错因。

**边界（尚未做）**：`assetRect` / `setRects`（遮挡与绕障用的矩形）**仍是纯 2D**，不认高度 ——
这是 Phase 2 的欠账，terrain 模式下同样存在，不是 Shift 引入的：
平面模式下用 Shift 垫高的盒子，参与绕障时仍会按它在地面的投影挡住路径。

> `screenToGround`（HTML 拖放进来的落点）**有意不传 `excludeIds`**：那条路径落地时
> 新资产还没进 `state.objects`，没有"自己"可排，传空集只是噪音。
> 一旦将来支持"从画布外拖回一个已存在的对象"，这里就必须补上。

### 9.7 团队整队也接上了 Shift（撤回 §9.5 的旧边界）

原边界写的是「`addGroupAt` 没有接 `forceTerrain`，Shift 拖入的队员仍落在 `y = 0`」。现在补上了，
顺带解决了一个不那么显然的问题：**团队落位不能只算锚点。**

- **逐个落位，不是批量摆放。** 每个队员走一次 `placeObject`，且**先并进 `staged` 再算下一个** ——
  后面的队员要能"看见"前面已经落好的。这不只是正确性问题，也顺手让"同点再来一个"表现为
  **叠上去**而不是被水平推开（§16 ② 把这个反直觉的行为钉住了）。
- **不给 `layerY`。** 锚点头顶拾到的那一层**不代表每个队员脚下那一层** —— 队员散在编队槽位上，
  可能一半在平台上、一半在地面（§16 ①）。所以各自按自己的 `(x, z)` 反查才是对的，
  这正是 `restingBaseY` 的 fallback 路径（"没给 layerY 就按落点反查"）存在的意义。
- **Shift 必须"存"进草稿，不能等确认时再读。** 拖放是**瞬时**的：松手那一刻弹出配置面板
  （人数 / 类型 / 编队），用户点「创建团队」时 Shift 早松了。所以 `groupDraft` 里加了 `terrain`
  字段，在 `handleDropAdd` 里就把 `event.shiftKey` 落进去。
  > 这是个容易复发的模式：**任何"手势 → 弹面板 → 确认"的交互，都会把手势级状态断链。**
  > 凡是靠 `event.shiftKey` 之类瞬时状态驱动的东西，跨过异步交互边界时必须显式携带。

用例在 §16（含"对象不在 `objects` 里 → `placeObject` 只回原坐标、不写 `baseY`"这条**契约**断言 ——
我写这组用例时第一版就踩了这个坑，顺手把它钉成契约，免得下次再踩）。

### 9.8 Phase 2 收尾 + Phase 3：障碍集合的 3D 化

这一轮做了两件事，都属于"**只改喂进去的东西，不改算法**"这一类。

#### ① 遮挡的 3D 化（Phase 2 收尾）

`occlusion.ts` 的 `blockingAssets` 原本是 2D `segIntersectsRect`（只看 x/z）。
新增 `segIntersectsBox`（3D slab / Liang–Barsky）与 `objectBox`，判定改用**实体盒**：

| 情形 | 2D 判定 | 3D 判定 |
|---|---|---|
| 高机位俯拍，视线从矮墙上方掠过 | 误报遮挡 ❌ | 不遮挡 ✅ |
| 桥下看对面，视线穿过桥体下方 | 误报遮挡 ❌ | 不遮挡 ✅ |
| 低机位平视 3m 墙 | 遮挡 ✅ | 遮挡 ✅ |

配套改动：
- **`occluding` 与 `blocking` 真正拆开**（字段本就在 `schema` 里，但 `blockingAssets` 只认 `role === "set"`）。
  玻璃 `occluding: false` 看得见对面，与"挡不挡路"是两件事。
- **两处调用都传真实高度**：`OcclusionHighlights` 用 `resolved.position[1]` / `resolved.target[1]`，
  `CameraHud` 同一套 —— 两处各写各的话，HUD 的警告会和画布上的红框对不上。
- **`OcclusionHighlights` 的红框与标签跟着 `objectBottom` 走**（原先写死在 `y=0`）。
  否则挡住二楼机位的道具会在脚下的地面位置画一个红框，指错了东西。
- `Vec3 | Vec2` 入参都接受，缺 `y` 按 0 处理 → 旧调用点平滑迁移，planar 逐值不变（§18 末条）。

#### ② `blockingRects`：3D 化避障的唯一支点（Phase 3）

新建 `engine/avoidance.ts`。**核心算法一行不改** —— 可见图、Dijkstra、`canStraddle`、
侧向分流、二次兜底全部原样。改的只是"喂进去的障碍集合"：

```
setRects（全集）
  → blockingRects（可达性过滤：迈得上 / 穿得下 / 语义开关）   ← 新增
  → canStraddle（编队骑得过）                                ← 一行不改
```

顺序不能反：`canStraddle` 问的前提是"它本来就是个障碍"，可达性过滤过的再判纯属浪费。
它的适用面因此自然收窄到"`Δh` 高到无法迈过的细高柱 / 树"，符合预期。

**`routeHeightFor` 是本轮最需要小心的一个设计。** 它给出"按哪一层来判断障碍"，取该对象
**所有段起始落脚高度的最小值**。三条理由里**第一条是决定性的**：

> **它必须与 `currentTime` 无关。** 否则障碍集合逐帧变化，`objectRouteCache` 的 key
> （`${revision}|${objectId}`）就退化成"每个时刻一份" → 缓存全废，每帧重跑可见图 + Dijkstra。
> 好消息：`routeHeightFor` 只读 `objects` / `segments`，而 store 的每次改动都会 `revision + 1`，
> 所以它在一次 revision 内是常量 —— **不需要额外把 fromY 量化进缓存 key**（04 §4 原本担心的问题
> 被这个设计直接消掉了，而不是靠量化绕过）。
> **代价是一条约束：改动 `routeHeightFor` 时绝不能让它读 `currentTime`。**
> §19 专门守这条 —— 谁破坏了它，测试立刻红。

取最小值还自带**保守方向**：判断的是"在最低处能被什么挡住" → 更多障碍判为阻挡 →
路径更保守 → 绝不穿模。代价只是可能多绕一段（已知误差，v1 接受）。

**两个障碍集合的职责拆分**（`solver.ts` 的 `groupInfluenceOffset`）：

| 用途 | 集合 | 理由 |
|---|---|---|
| ③ 侧向让位（意图） | `sets` = **过滤后** | 一个该迈上去的台阶不该引发侧让 |
| ④ 二次兜底 push-out（防穿模） | `solidSets` = **全集** | "无论如何不穿模"的地板，不能因意图过滤而失效 |

兜底用全集为何不误伤：它按 3D 语义判相交（相切不算冲突），人站在台阶上恰好相切 → 不推开。

**本轮没做**（刻意留下）：`maxJumpHeight` / 跳跃包络属 Phase 4。现在把"跳得过"的障碍剔掉
会让路径直穿过去、而人还不会跳 —— 那是穿模。等 Phase 4 落地弧线后在 `isPassable` 里加一行即可，
**这正是"只改集合"这个设计的收益**。`pushOut` 的 y 重算同理（它只服务路由前的起终点推出，
需要先有 `standable`，属 Phase 4 配套）。

#### ③ 三个测试教训（都是"测试写错了，不是代码错了"）

§17/§18 第一版有 3 条 FAIL，逐条查明**全部是我的用例写错**：

1. **`locomotionOfId` 对不存在的对象返回 `ZERO_LOCOMOTION`**（`height=1`、`maxStep=0`），
   不是"人的能力表"。我写用例时忘了把 actor 放进场景 → 断言基于错误的能力表。
   **教训：凡是走"按 id 查能力表"的断言，先确认那个 id 真的在场景里。**
2. **相切命中不算误报。** 我断言"12m 机位俯拍 8m 外的 3m 矮墙不遮挡"，但手算一下 ——
   视线在墙所在的 `z=2` 处恰好 `y=3`，是**相切**，判遮挡是对的。真正的"从上方掠过"要 20m。
   **教训：几何断言先手算一遍关键位置的值，再写下期望 —— 否则是在拿直觉对赌数学。**
3. 缓坡那条同 ①（`maxStep=0` 时 0.3m 当然迈不上）。

## 9.9 Phase 4：跳跃 / 落差 / 攀爬

一句话：**把"垂直对齐"从一个瞬时动作，升级成一条由作者定顶点、由系统验可行性的弧线。**
核心主张（02 §1）：跳跃不是一个物理参数，而是**由两个导演旋钮生成的可行性包络**。

#### ① 包络公式（`engine/jump.ts`）

UI 只暴露两个数 —— 原地起跳高度 `H`、平地助跑跳远 `R`（human 默认 0.9 / 2.5）。
从能量守恒推导（`vy0 = √(2gH)`、`T = 2vy0/g`、`vh = R/T`），取抛下降支，`g` 全部约掉：

```
reach(Δh) = R/2 · ( 1 + √(1 − Δh/H) )
```

性质（§20 全部钉死）：`Δh=0 → R`、`Δh=+H → R/2`、`Δh=−H → ≈1.21R`、
`Δh > H → 不可达`；**单调递减、上凸**。这条曲线是"跳跃距离怎么设计"的答案，
也应直接画给导演看（`Δh` 横轴 / `reach` 纵轴 + 当前路径那个点）—— 留待 Phase 5。

`classifyGap(dh, loco)` 把一段高差分档为 `flat / step / drop / jump / climb / blocked`，
**阈值全挂 `loco`**：同一级 0.3m 台阶，人 `step`、车 `blocked`（§22 同时断言这两条）。

#### ② 三种垂直弧线（`engine/arc.ts`）

| mode | 垂直曲线 | 用途 |
|---|---|---|
| `parabola` | `groundAtStart + apex·4s(1−s)` | 跳上 / 跳过（顶点作者可拖） |
| `fall` | `y0 + (y1−y0)·s²` | 落差下落（`s²` 才有重力加速感，线性像电梯） |
| `climb` | 三段 L 形贴墙（水平→竖直→水平） | 攀爬 |

**关键设计：apex 由作者定，可达性由包络校验。** 这是与"真物理"最重要的分歧 ——
不做"给初速自动算轨迹"（导演无法控制跳多高），而是**顶点作为作者旋钮**（UI 直接拖），
系统只做三条校验（§4）：`apex ≥ Δh`（不满足则**自动抬到 Δh**）、`apex ≤ H`、`dx ≤ reach(Δh)`。
失败**报错而不是默默画出来**。

**与水平速度解耦的收益**：轨迹是 `s` 的闭式函数，路径的 `ease` / `speedKeys`
**不需要为跳跃做任何改动** —— 跳跃自动跟着路径走向走。这是"垂直三级权威"的直接兑现。

`arc.ts` 的函数**只读弧线自身参数**，不读 `state` / `currentTime` ——
与 `routeHeightFor` 守同一条"时间无关 ⇒ 可按 revision 缓存"的红线。

#### ③ 高度权威：`engine/pathHeight.ts`

Phase 4 之前，"对象画在多高" = `standingHeightFor`（脚下几何派生，落差**瞬时对齐**）。
现在多了一个来源：**段上的弧线**。合并规则的**唯一定义处**在 `pathHeightAt`：

1. **弧线**（该段有 `arc` 且地形世界 或 段标了 `arcAlways`）→ `u` 的纯函数；
2. **瞬时对齐**（`standingHeightFor`）→ 老路径。

**planar 逐像素不变**：planar 下弧线默认不生效（`arcActive` 要 terrain 或显式 `arcAlways`），
于是永远走第 2 条，而 planar 的 `maxStep=0` 使 `standingHeightFor ≡ object.baseY ?? 0`。
§22 钉死这条。渲染（`WorldView` 的 actor `useFrame`）与轨迹线（`arcPolyline`）都改走这里。

- **`arcAlways` 的意义**：类似 Shift 覆盖 —— 是**作者显式意图**，不是世界模式的替代品。
  它让"我想在这个平面场景里也画一条跳跃弧"成立，而不必把整个场景切成 terrain。
- **轨迹线跟着弧线鼓起来**：`arcPolyline` 按归一化里程取弧线高度，
  于是"跳过去"这件事一眼可见（不是一条贴地的线）。

#### ④ 助跑（02 §5）：一个 bug 变成表达手段

默认 cubic-bezier 在 `u=0` 处**斜率为 0** → 人原地弹起原地落下，看起来完全不像跳跃。
三层解法落地了两层：

1. **跳跃段内强制准线性水平速度**：`setSegmentArc` 写入弧线时**同时**把该段 ease 覆盖成
   `JUMP_EASE = [0.15,0.15,0.85,0.85]` —— 落成**一个原子 store 动作**，作者不会漏。
2. **有效跳远随实际速度缩放**：`reachEffective = R · mix(0.5, 1.0, speedRatio)`，
   站着跳只有一半远。`checkJumpArc` 在 `speedRatio < 0.6` 时报 `needsRunup`。
   **这一条把"助跑"从缓动端点的 bug 变成了可调的表达手段。**

（第 3 层"检查起跳点瞬时速度"的完整求解器接线属 Phase 5 的 UI 提示。）

#### ⑤ 落地校验（02 §7）

- **轨迹不相交**：`sampleArcHits` 沿弧线按 0.1m 步长采样，第一个落在盒 `[bottom, top]` 内的
  采样点即撞点（§22：弧顶 0.4 撞 0.5m 墙、抬到 0.9 掠过）。
- **落点站得住**：`standingAt` 取落点处最高可站立面（与 `pathHeight` 的落点面同源），
  基准面 0 恒成立（§22）。
- **`runupAdjusted` / `runupMarginU`**：起跳点应**早于**起跳面边缘、落点应**晚于**落点面边缘
  （默认 0.25m）—— 否则人会"先踏空再起跳"，像从悬崖上掉起来。

#### ⑥ UI（`Inspector`）

选中 MOVE 段、主体是 agent 时出现「垂直弧线」字段：显示本段高差 / 跨度 / 分档判定，

上坡不能选下坠、平地不能选攀爬），抛物线模式多一个**弧顶高度滑杆**（上限 = `H`），
以及校验 `issue` 与 `needsRunup` 的红 / 橙提示文案。

#### ⑦ 测试教训（又是"测试写错了"）

1. **`locomotionOf` 在 planar 下整体退化成 `PLANAR_LOCOMOTION`** —— 我用 `scene([...])`
   （缺省 planar）取"人的能力表"，拿到的是 `maxStep=0、不会跳`，于是所有 `classifyGap`
   都判 `blocked`。**这与 §17 是同一个坑**（当时是"id 不在场景里 → `ZERO_LOCOMOTION`"，
   这次是"在场景里但场景是 planar"）。→ **教训：取真实能力表，必须建 terrain 场景。**

## 9.10 Phase 8（部分）：堆叠拖动传播 / 失支撑即落

一句话：**「谁压在谁上面」不存成关系记录，而是每次从几何现推；拖动 = 整塔按根的位移
一起走，失支撑 = 自下而上重新落。**

起因是一个用户报的 bug，「堆叠后拖走最下层，上层不动、悬在空中也不落下」——
直接违反 INV-3D-04（`baseY` 必须等于下方支撑面顶面）。

#### ① 为什么用几何推导，而不是文档 §5 原本提的 `Support { upper, lower }` 记录

判据完全是绝对几何：`upper.bottom ≈ lower.top`（相切）**且** `footprintsOverlap`
—— 这就是 INV-3D-05 说的"相切 = 堆叠"。于是：

- 持久化关系记录会引入**第三个真相来源**（几何、`baseY`、关系三者不一致时谁赢？）。
  几何推导只有一个来源，与"`baseY` 存绝对值"是同一种"少一份要同步的状态"的思路。
- 文档要 `Support` 是为了"求解器能纯函数复算"；草掉它，纯函数性质只会更强
  —— **求解器连推导函数都看不到，只有编辑器（store）用**。
- 将来性能需要可以把推导结果缓存（key 挂 `revision`），但**不要**把它变成可编辑的持久数据。

#### ② `engine/stack.ts`（新）

| 函数 | 语义 |
|---|---|
| `restsOn(upper, lower)` | 相切 + 水平重叠 + 都是 `set`（人不是几何的一部分） |
| `objectsOnTop(state, id)` | **直接**压在上面的那一层 |
| `stackChain(state, id)` | 从 `id` 起 BFS 向上收整条链，**根在最前** |
| `translateStack(state, id, dx, dz)` | 只移 x/z —— 整塔平移时层间相对高度不变 |
| `settleStack(state, chainIds)` | **自下而上**重新推导各层 `baseY`，**只降不升** |

#### ③ 两个不变量比想象中细：排除规则与 bottom 联动

这两条都是回归测试（§23）第一版抓出来的，一开始都想错了：

1. **排除集 = `{自己} ∪ {链内更高的层}`，而不是整条链。**
   塔整体平移后各层相对位置没变 —— A 仍在 B 正下方。若不排除自身，复审 B 时
   "A 的顶面正好接住我"→ 判定不用动，整塔踩空却谁也不落（用户报的就是这个）。
   但**排太多**（排掉整条链）同样错：B 落定后无法成为 C 的支撑，C 穿过 B 落到地上。
   正确做法是利用"自下而上"这个处理顺序 —— 轮到 X 时，**比 X 低的层已经落定**，
   它们就是 X 的真实新支撑，必须保留；只有比 X 高的层（高度还是旧的）要排除。
2. **`bottom` 是绝对世界高度，改 `baseY` 时必须同步平移 `bottom`。**
   `bottom` 不是相对 `baseY` 的偏移（schema 明确写"世界米"）。拱洞对象
   （`baseY 2.4 / bottom 1.75`，下探 0.65）落到地面后应是 `baseY 0.65 / bottom 0`，
   而不是 `baseY 0.65 / bottom 1.75`。**保持的是"下探量"，不是"bottom 的绝对值"。**

另外 `settleStack` 的支撑查询直接复用 `ground.ts` 的 `supportUnder`（`maxStep = 0`
= 只接"顶面 ≤ 当前底面"的面），因此"点在哪里落、塔就落在哪里"与 `placeObject` 同源。
注意它的桶索引**按 `state.objects` 引用缓存**，所以每次都用当前数组现构 state，不能跨迭代复用。

#### ④ 三条 store 路径的接线（`state/directorStore.ts`）

| 动作 | 传播内容 |
|---|---|
| `moveObject` | 按根的 Δ(x,z) **和 Δy** 传播整条链，再 `settleStack` 兜底。**Δy 也必须传**：塔被抬上平台时上层若不跟着抬，会嵌进根部（塔被压扁），而 `settleStack` 只"掉"不"抬"，修不了 |
| `updateAsset` | 改 `footprint`（尤其 `h`）后复位压在它上面的链 —— 薄板变厚会嵌、变薄会悬空 |
| `removeAsset` | 删底座后把原来的上层链向下重新落位（同一个 bug 类，只是经由删除触发） |

**planar 逐像素不变**：`baseY === undefined` 就是"非 terrain"的判据（`placeObject` 在
planar 不写 `baseY`），此时 `stackMode = false`，整条新逻辑一行不进。

#### ⑤ 测试教训（第三次"测试写错了"）

§23 第一版 6 条 FAIL，逐条查明**全部是用例写错**，而不是实现错：

1. **"拖走整塔 → 三层一起落回 0"是错的预期。** 刚性平移后塔是完整的，
   各层仍互相压着 → 应保持 `[0,1,2]`（并断言 `settleStack` **零改动、引用相等**）。
   真正"失支撑"的场景是**删掉底座**，不是把底座搬走（搬走时上层跟着走）。
2. **"整塔搬到平台 → 三层 1/2/3"不能只调 `settleStack`。** "抬"是 `placeObject` 的职责，
   `settleStack` 只负责"掉"。用例要按 `moveObject` 的真实分工写：根部 `placeObject` 定高 +
   上层同步抬 Δy，最后才 `settleStack`。**这条用例同时暴露了 `moveObject` 漏传 Δy 的真 bug。**
3. **拱洞期望值算错**：以为落到地面后 `bottom = -0.65`。正确是 `bottom = 0`
   （实体贴地），**保持的是下探量 0.65**。

## 9.11 Phase 8 收尾：阵列（批量复制）+ 列表折叠

一句话：**不再逐个手工摆，而是"说清楚要几份、怎么排"；堆叠塔在列表里也不再各自一行。**

#### ① 阵列只落"意图"，不落"几何"（`engine/array.ts`）

新增的 `engine/array.ts` 是**纯函数**：给源对象 + 规格，算出 N 个目标落点。
它不读 `state`、`currentTime`，不做射线查询 —— 与 `arc.ts` / `routeHeightFor` 守同一条红线。

| kind | 语义 | 由谁决定高度 |
|---|---|---|
| `line` | 沿一条直线依次排开 | `placeObject` 反查支撑面 |
| `grid` | 矩形阵列 rows×cols | `placeObject` 反查 |
| `stair` | 逐级抬高的台阶 | **作者显式给 `baseY`** |
| `ring` | 等角度绕一圈 | `placeObject` 反查 |

**唯一例外是 `stair`**：台阶的抬高量是作者的显式意图（"我要一级 0.15m"），
不是几何反查的结果，所以它自己带 `baseY`，交给 `placeObject` 当 `layerY`（已知年代初那条：
调用方显式给了标高时它就是权威）。其余三种一律不带 `baseY` ——
**这是 planar 逐像素不变的守卫**（§24 钉死：非 stair 一律 `baseY === undefined`，
否则就绕过了 `placeObject` 的"非 terrain 不写 baseY"判据）。

两条契约：
- **第 0 个槽位 = 源对象当前位置**。于是"原地保留源 + 追加 N−1 个副本"就是
  `arraySlots(...).slice(1)`，"整组重排"则用全部 —— 两种 UI 共用同一份几何。
- **`count` 是总数（含源自身）**，与 Blender 数组修改器同义。UI 的按钮文案
  显示的是"新增 N−1 份"而不是 N —— 预览与实际生成同源（都问 `arrayCount`）。

#### ② store `arrayAsset` 复用"逐个先并进 staged 再 placeObject"

与 `addGroupAt` 同一个模式：**后面的副本要能看见前面的**，否则它们会重叠在同一个格子上。
每个副本独立走 `placeObject` ⇒ 在 terrain 世界里自动各自贴到脚下的台面。

拱洞（`bottom < baseY`）的副本：**保存"下探量"而非 `bottom` 的绝对值**
（与 §9.10 ③ 那条不变量一致），落位后用真实 `baseY` 重算一次。

源若是某座塔的根，**只复制它那一个对象**，塔不会被整座搬过来 —— 阵列的语义是"复制这个体块"。

#### ③ 列表折叠：几何关系不能越过"谁被渲染"这个前提

`stack.ts` 新增 `stackParentMap` / `isStackBottom`。ObjectList 由此把堆叠链折叠成一行，
并给父行配上**整塔的隐藏 / 锁定 / 删除**（没被压着时行为完全不变）——
这正是"折叠成一行"的意义：导演眼里这一行就是那一座塔。

踩到一个坑：**不能无条件按几何关系隐藏子层。**
若一座塔压在一个"被团队行合并掉的队员"身上，那个父行根本不渲染，
子层却被隐藏 ⇒ **整座塔从列表里彻底消失**。
判断必须写成"父行真的在列表里时才并入它的子树"（`hiddenUnder`）。

另一个细节：横跨两块等高板的盒子，只认**顶面最高**的那块当父 ——
树（Tree）而不是 DAG，否则同一层会在列表里出现两次。

视觉上刻意区分两种子树：**时间轴片段**用实线引导（时间轴概念），
**堆叠层**用橙色虚线（空间轴概念）—— 两根不同的轴不该长得一样。
