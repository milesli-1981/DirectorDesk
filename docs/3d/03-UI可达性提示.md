# 03 · UI：如何告知"这里要跳跃""这里要攀爬"

> 本文回答：导演在画布上怎么**看见**可达性问题，以及怎么**修**它。
> 原则：**先说人话，再给数字，最后给一键修复。** 硬阻止是最差的选择。

---

## 1. 可达性分级

| 档 | 条件 | 文案 | 线色 / 线型 | 图标 |
|---|---|---|---|---|
| **0 可走** | `Δh ≤ maxStep` | （不提示） | `#f0a35a` 虚线（**现状不动**） | — |
| **1 需跳跃** | `maxStep < Δh ≤ maxJumpHeight` 且 `dx ≤ reach(Δh)` | 「需跳跃」+ 高度 / 跨度 | `#ff9f0a` **实线** | 弓形 |
| **2 需攀爬** | `maxJumpHeight < Δh ≤ maxClimbHeight` 且有抓手 | 「需攀爬」 | `#bf5af2` 点线 | 抓手 |
| **3 不可达** | 超出攀爬上限，或跨度超包络 | 「不可达」+ 原因 | `#ff453a` **密集虚线** | 叉 |
| **4 站不稳** | `overhang ≥ 0.2` | 「站不稳」（弱） | `#8e8e93`（弱） | 波浪 |
| **5 站不直** | 净空不足 | 「这里站不直」 | `#8e8e93`（弱） | — |
| **6 落差** | `Δh < −maxStep` | 「下落 x.x m」 | `#ff9f0a` 实线 + `fall` 弧 | 下坠 |

**颜色全部取自项目现有色板**（`styles.css`：`--ap-orange:#ff9f0a`、`--ap-purple:#bf5af2`、`--ap-red:#ff453a`、`--ap-text-3:#8e8e93`），没有新造颜色。而 0 档刻意保持 `#f0a35a` 虚线不动 —— **现有场景的视觉零变化**是硬要求。

### 色盲与可读性

**不能只靠颜色区分。** 每档都同时改变**线型**（虚线 / 实线 / 点线 / 密集虚线）和**图标形状**（无 / 弓形 / 抓手 / 叉），粗细也分档（可走 1.5 / 需跳跃 2 / 不可达 2.5）。这样在灰度下依然可读。

## 2. 路径着色：从"一条橙线"到"按可达性分段"

现状 `SegmentPaths`（`WorldView.tsx:651-665`）把整条绕行路线画成**一条**橙色虚线。

改造：把 `route` 折线**按可达性切段**，每段独立着色。判定来源就是 [01 §6](./01-物体与判定.md#6-移动判定沿路径连续采样) 的 `walkLeg` —— 沿路径采样时顺手记录每一段的档位，**不额外计算**。

```
[0.00 – 0.34]  可走      虚线橙
[0.34 – 0.52]  需跳跃    实线亮橙 + 抛物线
[0.52 – 0.71]  可走      虚线橙
[0.71 – 1.00]  不可达    密集虚线红
```

**关键**：分段用的折线必须**与求解共用**（现在是 `segmentRoutePoints` + `routeObstacles`，`WorldView.tsx:657-658`）。一旦分叉，就会出现"线是绿的、人却过不去"这类不可调试的 bug —— 这是现有代码已经在注释里强调过的约束（"两边必须一致，否则会看到橙色线绕行、人却直穿过去"）。

**跳跃段的线要画成 3D 抛物线，不是平的。** 现在所有路径线都写死 `y = 0.13`（`WorldView.tsx:659`）。跳跃段必须用 `y(u)` 的实际值 —— 这本身就是最直观的"这里要跳"提示。

## 3. 跳跃弧线预览（整套 UI 里最重要的一件）

把弧线直接画进画布，所见即成片：

- **轨迹**：按 `y(u)` 采样，`Line points = [x(u), y(u), z(u)]`，实线亮橙
- **顶点把手**：顶点处一个可拖的球（垂直拖 = 改 `apex`），交互与现有 `PointMarker`（`WorldView.tsx:805-815`）一致 —— 复用同一套 hover 放大 / 变亮 / 指针捕获
- **高度标尺**：从顶点向下画一条虚线到地面，旁标 `顶点 1.2m`
- **标签**：顶点旁 `Html` 标签 —— `跳跃 · 高差 +0.85m · 跨度 1.4m`
- **落地校验失败时**：轨迹变红 + 在撞点处放一个叉

这样导演看到的形状**就是观众会看到的人的运动轨迹**，而不是一个抽象图标。

## 4. 场景内可点徽标：直接复用 `HandoffBadge` 的模式

`HandoffMarkers`（`WorldView.tsx:854-897`）已经是一个完美的模板：

```tsx
<Html position={[x, 1.05, z]} center style={{ pointerEvents: "auto" }} zIndexRange={[45, 0]}>
  <button className="handoff-badge" style={{ borderColor: color, color }} ...>
    {glyph}
  </button>
</Html>
```

跳跃 / 攀爬徽标照抄这个结构：

- **位置**：弧段**中点**上方 1.05（与 handoff 同高，但 handoff 在**路点**处、跳跃在**段中**，位置天然错开不打架）
- **点击** → 小型菜单：`生成弧线` / `改为攀爬` / `改为绕行` / `删除`
- **拖拽** → 直接改 `apex`（同 §3 的顶点把手，徽标只是它的可点外壳）

### 为什么必须是 DOM（`Html`）而不是 WebGL sprite

`NameTag` 的注释（`WorldView.tsx:152-156`）写得很清楚：它特意用 sprite + CanvasTexture，**因为 DOM 覆盖层录不进导出视频**，而名牌需要出现在成片里。

反过来用这条规则：**可达性提示不该出现在成片里** → 用 `Html`（DOM）正是正确的选择。再加上外层已有的 `showHelpers = viewMode === "director"`（`WorldView.tsx:614`），导出的视频天然干净。

> 这条"DOM = 导演视图 / WebGL sprite = 进成片"的隐含约定，值得写进项目文档，因为后面的 Phase 都会用到。

## 5. Inspector 可达性面板

选中演员 → 新增「可达性」分区，逐段列出：

```
MOVE 1  0.0s – 3.2s   可走
MOVE 2  3.2s – 4.8s   需跳跃   高差 +0.85m · 跨度 1.4m   [生成弧线]
MOVE 3  4.8s – 6.0s   不可达   高差 +2.6m 超出攀爬上限 1.6m
                              [改为绕行] [加中间落脚点] [降低落差]
```

- 每行**可点击** → 镜头飞到该段 + 选中该段
- `[生成弧线]` 直接写 `vertical: { mode: "parabola", apex: Δh + 0.15 }`（带一点余量，视觉上更安全）
- **失败行必须给出"改哪个对象"**：例如「降低落差」悬停显示 "把「石墙」高度从 3.0m 降到 1.4m 或以下"

### 一键修复的四种动作

| 问题 | 修复动作 | 实现 |
|---|---|---|
| 需跳跃 | **生成弧线** | 写 `vertical: parabola`，`apex = Δh + 0.15`，默认时长由包络推算 |
| 跨度太远 | **加中间落脚点** | 在路径中点附近找最高的可达面，插入一个路点 + 自动分成两段弧线 |
| 太高（但攀得上去） | **改为攀爬** | 若 `Δh ≤ maxClimbHeight` 且有抓手 → 换 `mode: "climb"` |
| 完全不可达 | **改为绕行** | 在该对象上加 `prefer: "walk-around"`，走现有绕障（见 [04 §3](./04-避障兼容.md#3-跳过去-vs-绕过去的歧义)） |

**"一键修复"是这个工具的核心价值** —— 导演表达意图（画一条直线过去），系统负责把它变成可行方案。这与项目既有的"导演语言不暴露原始数值"（`STYLE_PRESETS` 注释）一脉相承。

## 6. 即时反馈（拖拽时）

拖路径点 / 端点 / 物体时，实时算可达性：

- 落到不可达位置 → **光标变红、端点球变红、tooltip 说明原因**
- **允许放下**（不要硬阻止）。导演可能故意留一个断点当作待办；硬阻止会让人恼火，且会挡住"先摆好位置再调几何"的工作流
- 放下后**持续标红** + Inspector 里列出 + 徽标保留

**文案（说人话，带数字）**：

> ❌ 「不可达 (code 3)」「Δh 超阈值」「reach < dx」
> ✅ 「这里落差 2.6 米，超过攀爬能力 1.6 米」
> ✅ 「跨度 3.1 米，最远只能跳 2.5 米」
> ✅ 「跳得过去，但要在跳之前助跑」

## 7. 时间轴

- MOVE clip 内**叠加一条 mini 弓形曲线**，顶点可上下拖（改 `apex`）
- 跳跃期间给 clip 加**斜纹底纹**，表示"离地"
- hover 显示「离地 1.2m / 滞空 0.7s」
- 这复用现有 `EaseEditor`（`components/EaseEditor.tsx`）的画法，只是曲线来源换成 `y(u)`

**落地实现（Phase 7）**：

- 弓形**不是** `y(u)` 的控制点曲线，而是**离地量的时间曲线**：采样 17 点
  `pathHeightAt − standingHeightFor`（即 `stance.ts` 的 `airborneOf`），
  按 `peak` 归一化 —— 于是时间轴上的形状与画面里飞的弧线**同一个来源**（红线 5）。
  实现：`stance.ts` 的 `flightProfileOf` + `Timeline.tsx` 的 `arcSpark`。
- 底纹是 CSS `repeating-linear-gradient`（115° 绿斜纹），**不是** svg `backgroundImage` ——
  因为弓形也要用 `background-image`，两者叠在一层会互相覆盖。
- 采样只在**真的离过地**时输出（`peak > AIRBORNE_EPS`），平地 / planar 下 `flight === null`
  ⇒ 时间轴不多出任何元素，逐像素不变。
- **顶点拖拽改 `apex` 尚未做**（需从 DOM 反推像素 → 高度，属后续）。

## 8. 包络图：把"能不能跳过去"变成一眼可见

Inspector 里放一张小图（Δh 横轴 / `reach` 纵轴）：

- 一条单调下降的曲线 `reach(Δh) = R/2·(1 + √(1 − Δh/H))`（见 [02 §3](./02-跳跃与攀爬.md#3-跳跃包络本文的核心公式)）
- 当前路径的 `(Δh, dx)` 画成一个点
- 点在曲线**下方** → 绿（跳得过去）；**上方** → 红（跳不过去）
- 曲线在 `Δh = H` 处触零 —— 直观说明"跳得越高，能跳的横向距离越短"

比一串数字强得多，也是把这个公式**教给导演**的最好方式。

## 9. 全局可达性体检

工具栏一个按钮：**扫描全场景所有 agent 的所有 segment**，列出：

```
3 处需要跳跃 · 1 处不可达 · 2 处站不稳
```

## 10. 相机跟跳的防抖

FOLLOW 一个跳跃目标时，相机的 y 会剧烈上下，画面会颠。

现有 `CameraObject.stabilize`（`schema.ts:303-308`）是对机位 / 注视点做滑动平均，但**水平与垂直混在一起**。

**两个方案**：

| 方案 | 做法 | 观感 |
|---|---|---|
| **a. 垂直分量分离** | `stabilize` 增加垂直系数（默认 垂直 0.7 / 水平 0.2） | 镜头平滑上升，不颠 |
| **b. 跳跃时锁高度** ✅更电影 | 目标离地期间，相机保持起跳高度的水平轨道，**不跟高度** | 像真实跟拍：人跳起来冲出画框又落回来 |

**推荐 b** ✅**已落地**，并做成相机上的一个开关（`CameraObject.followJumpHeight?: boolean`）。理由：这是**电影语言**层面的选择，不是参数调优 —— 跟拍时摄影师本来就不会跟着人跳。而 a 只是"让抖动小一点"，没有表达力。

### 落地后的实现要点（Phase 6）

- **默认 `true` = 跟随**，保持扩展前的逐值行为；`false` 才锁高度。开关在 Inspector。
- **判"离地"** = `pathHeightAt`（实际高度，含弧线）− `standingHeightFor`（脚下地面）> `AIRBORNE_EPS (0.01)`。
  对段上弧线与"走出平台边缘的落差"都自动生效。
- **锚线 = 起跳点脚下的地面**（`cameraAnchorHeight`）。不是 `bodyHeightOf(takeoff)` ——
  二分到的是"离地量首次超过 1cm"的时刻，那一刻实际高度天然比地面高约 1cm，
  拿它当锚线会让锁定期间镜头缓慢上抬。二分取**贴地侧**端点。
- **只在 OBJECT / OTS 生效**：GROUP / POV / LOCATION 不存在"跟跳"。
- 几何自检 §29（7 例）钉住这四条边界。

> 与之配套的还有本 Phase 的**相机体系相对化**（六处绝对米数 → `lift + VIEW_HEIGHT`）
> 与**相机避障**（机位落进遮挡盒即推出），见 [00-总纲 §9.13](./00-总纲.md)。

## 11. 组队徽标归并

编队是路径弧长参数化的（`solver.ts:335-343`），所以整队会各自在自己的弧长处跳（见 [02 §10](./02-跳跃与攀爬.md#10-组队跳天然工作不需要额外代码)）。

**但徽标只画一个**：在锚点段的弧上。否则一队 5 人会冒出 5 个徽标，把画布糊住。

### 落地时补上的两条前提（不在原计划里，但不做则本 UI 是死代码）

1. **`blockingRects` 的"跳过去"排除**（[04 §2](./04-避障兼容.md)）。原计划假定"路径会穿过可跳的障碍"，
   但 Phase 3 的 `blockingRects` 当时把所有 set 都当障碍 ⇒ 路径永远绕开 ⇒
   分档永远报不出"需跳跃"。补上"顶面在包络内 + 跨度在跳远内 ⇒ 不进障碍集合"之后，
   §5 的 `[生成弧线]` 与 §2 的橙色线才有对象。
2. **`prefer: "walk-around"`**（04 §3 的逃生口，原本只有一个名字）。有了它，
   §5 的「改为绕行」才是一个能写回场景的动作，而不是一句提示。

### 一处必须记下的取值陷阱

`tierOfGap(0, dx)` 的 `reach` 是 **0**，不是 `dx`：平地上谈不到"跨度"。
写测试时若按直觉期望 `reach === dx` 会得到一个假失败（§26 已钉住这条）。
