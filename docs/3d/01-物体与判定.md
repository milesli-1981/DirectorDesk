# 01 · 3D 物体与站立 / 移动判定

> 本文回答两件事：**3D 物体怎么设计**、**怎么判断人物能不能站在上面、能不能走过去**。
> 末尾附 **25 个 case 的完整判定矩阵**。

---

## 1. 物体形态

同一个 `DirectorObject` 通过字段组合表达六种形态：

| 形态 | 字段组合 | 典型用途 | 参与绕障 |
|---|---|---|---|
| **方块 Box** | `baseY` + `footprint.h` | 台阶、平台、墙、桌子、箱子、建筑 | 是（若够不着） |
| **坡道 Ramp** | `+ topShape:"ramp"` + `rotation` | 斜坡、无障碍坡道、草坡 | 坡度 > maxSlope 时 |
| **拱桥 Arch** | `+ bottom < baseY` | 桥、门洞、管道、过街天桥 | 净空不足时 |
| **地形 Terrain** | `+ grid`（`category:"terrain"`） | 丘陵、谷地、沙丘 | 坡度 > maxSlope 时 |
| **阵列 Array** | `+ array{count, stepX/Y/Z}` | 楼梯、栏杆、货架、柱廊 | 展开后逐个判定 |
| **不可站立面** | `+ walkable:false` | 水面、泥沼、传送带 | 水平不挡、竖直不站 |

**阵列是必须的**：20 级台阶若各自成一个对象，对象列表会彻底淹没。`array` 让一个对象展开成 N 个盒 —— 列表里 1 行，求解侧展开成 20 个。

## 2. 字段语义与不变量

| 字段 | 含义 | 默认 | 约束 |
|---|---|---|---|
| `baseY` | 实体底面高度（世界米） | `0` | ≥ 0 或负（地下室） |
| `footprint.h` | 实体高度（**语义已升级为实体范围**） | 按类别预设 | ≥ 0 |
| `bottom` | 实体底面下探高度 | `= baseY` | ≤ `baseY` |
| `topShape` | `"flat"` / `"ramp"` | `"flat"` | ramp 需 `rotation` 定坡向 |
| `grid` | 高度场，取代平面顶面 | — | 仅 terrain 类 |
| `walkable` / `blocking` / `occluding` | 三个正交语义开关 | 全自动推导 | 见 §4 |
| `prefer` | `"jump"` / `"walk-around"` | 按能力推导 | 见 [04](./04-避障兼容.md#3-跳过去-vs-绕过去的歧义) |

### 不变量

| 编号 | 不变量 | 违反后果 |
|---|---|---|
| **INV-3D-01** | `bottom ≤ baseY ≤ baseY + h` | 几何自相矛盾 |
| **INV-3D-02** | `topShape === "ramp"` 要求 `h > 0` | 零高坡道无意义 |
| **INV-3D-03** | `grid` 对象必须 `topShape === "flat"` 且 `h === 0` | 两套顶面定义打架 |
| **INV-3D-04** | `baseY` 必须等于下方支撑面顶面，或标记为手工锁定 | 悬空 / 陷地 |
| **INV-3D-05** | 同一 `(x,z)` 上任意两对象的 `[bottom, top]` 区间**不得部分重叠**：要么完全分离，要么一个完全包含另一个 | **高度歧义**（站在哪个面上？） |
| **INV-3D-06** | `maxStep < maxJumpHeight < maxClimbHeight` | 能力档位错乱 |
| **INV-3D-07** | set 资产的 `rotation` ∈ {0, 90, 180, 270} | AABB 不再精确（见 §3） |

**INV-3D-05 是最重要的一条。** 它把"堆叠"和"冲突"区分开：

- **相切**：`B.bottom === A.top` → 这是**堆叠**，合法。
- **相交**：`B.bottom < A.top < B.top` → 这是**冲突**，报错。

用**严格相交**判定（`>` 而非 `≥`）即可自然区分。这会在 §5 的碰撞分离里再次用到。

## 3. 三个语义开关（不要全自动，也不要全手工）

默认全自动推导，只在语义特殊时 override：

| 物体 | `walkable` | `blocking` | `occluding` |
|---|---|---|---|
| 水面 | **false**（可涉水不可站立） | false | false |
| 灌木 / 草丛 | 自动（矮则上，高则挡） | **false**（可穿行） | 自动 |
| 玻璃 / 幕墙 | 自动 | true | **false**（不挡视线） |
| 栅栏（可看不可过） | 自动 | true | **false** |
| 传送带 / 移动平台 | true | false | 自动 |
| 碎石堆 | 自动 | **false**（可踩过去） | 自动 |

> 注意 `occluding` 与 `blocking` 是**独立**的。现在代码里"遮挡体"与"障碍"共用同一份 `role === "set"` 集合（`occlusion.ts:46-54`），3D 后必须拆开 —— 否则栅栏会挡住镜头，这在电影语言里是错的。

## 4. 旋转：一个必须一起修的既有 bug

**现状**：`assetRect()` 是轴对齐 AABB（`occlusion.ts:10-12`），`separateSetAsset`（`collision.ts`）也假设轴对齐。但 `rotation` 在渲染里是生效的（`WorldView.tsx:279`），**碰撞与遮挡完全忽略它**。

结果是：把一个 10×1 的墙旋转 90°，视觉上转了，障碍还是原来那个轴对齐盒。这不是新问题，是现在就存在的隐藏 bug —— 3D 化时必须一起决定。

### 已修的部分（Phase 1 顺带）

判定链**上游**的几处已经改成按局部坐标（`rotation` 生效），因为不做就没法正确拾取：

| 位置 | 状态 |
|---|---|
| `ground.coversXZ`（点是否在对象水平轮廓内） | ✅ 局部坐标 |
| `ground.objectHalfExtents` + 桶索引分桶范围 | ✅ 旋转后外接盒（OBB→AABB） |
| `raycast.rayObjectBox`（射线-盒） | ✅ 先把射线变换到局部坐标系 |
| `occlusion.assetRect` / `collision.separateSetAsset` | ❌ 仍是未旋转 AABB（Phase 2） |

> 这里有个踩过的坑：桶索引最初直接拿 `footprint.w/d` 分桶，理由是"轴对齐外接盒是旋转矩形的超集"。
> **这是错的** —— 转 90° 后墙铺在 `z ∈ [-5, 5]`，按原 footprint 只覆盖 `z ∈ [-0.5, 0.5]`，
> 后半截查不到对象，表现是"墙转过之后人能从它中间穿过去"。必须用 `objectHalfExtents()`。

### 剩余部分（Phase 2 一起做）

| 方案 | 做法 | 代价 |
|---|---|---|
| **a. 限制 90° 步进** ✅推荐 | set 资产 `rotation` ∈ {0,90,180,270}，此时 AABB 精确（只需交换 w/d） | 失去任意角度摆放 |
| b. OBB 有向盒 | `assetRect` → OBB，段-盒相交改写 | **可见图报废**：`pathfinding` 的四角节点假设轴对齐，整套绕障要重写 |
| c. 旋转外接 AABB | 保守放大 | 45° 时误差 41%，通过性极差 |

**选 a。** 理由：可见图（`pathfinding.ts:88-97` 的四角节点）是绕障系统的地基，OBB 会让它整体失效；而建筑 / 台阶 / 墙几乎都是正交摆放，90° 步进足够。

**坡道怎么绕？** `ramp` 用 `rotation` 决定坡向（任意角度），但它的**水平包围盒仍取旋转后外接盒**（保守但可用）。坡只在**顶面高度采样**里参与：`heightAt` / `raycast` 把世界坐标转到物体局部坐标，再沿局部 +Z 从 `bottom` 线性插到 `top`。这样绕障依然走 AABB，站上去的高度却准确。

## 5. 站立判定链

> **已实现到哪一步（Phase 1 结束时）**：第 1 步「候选面」的几何部分已经能用了 ——
> `engine/ground.ts` 的 `supportUnder` / `groundHeightAt` / `restingHeightAt` / `standingHeightFor`
> 回答"覆盖该点的最高可达面"，`engine/raycast.ts` 的 `raycastGround` 回答"射线指向哪个面"。
> 第 2~5 步（坡度、落脚面积采样、头顶净空、语义）**都还没做**，属于 Phase 3/4。
> 换句话说：现在能站对高度，但还不会告诉你"这里站不站得稳"。下面的 `standable()` 是目标形态。

核心 API：

```ts
// engine/ground.ts
export interface StandResult {
  ok: boolean;
  /** 落脚面高度（ok 时有效）。 */
  y: number;
  /** 支撑对象 id（null = 基准面）。 */
  supportId: string | null;
  /** 该面坡度（度）。0 = 水平。 */
  slopeDeg: number;
  /** 脚底采样点中不落在支撑面上的比例 0..1。 */
  overhang: number;
  /** 失败原因（ok=false 时）。 */
  reason?: "no-surface" | "too-high" | "too-steep" | "no-clearance" | "not-walkable";
}

export function standable(
  state: DirectorState,
  x: number, z: number,
  fromY: number,
  loco: Locomotion,
): StandResult
```

判定链 —— **五步全过才算可站立**：

### 第 1 步 · 候选面

`groundHeightAt(state, x, z, fromY, loco.maxStep)` 取覆盖该点、且 `top ≤ fromY + maxStep` 的**最高面**。

排除条件（任一命中即不是候选）：
- `walkable === false`
- 被另一个对象的 `[bottom, top]` 区间**完全包含**（INV-3D-05 允许的嵌套情形 → 取最内层）

### 第 2 步 · 坡度

| 顶面 | 坡度算法 |
|---|---|
| flat | `0°` |
| ramp | 局部坐标下 `atan(h / footprint.d)`，按 `rotation` 的方向为坡向 |
| grid | 中心差分求梯度：`atan(‖∇h‖)` |

要求 `slopeDeg ≤ loco.maxSlopeDeg`。超了 → `reason: "too-steep"`，该对象**退化为墙面**（这是"陡坡不能走"的实现方式：不引入新概念，同一个几何既是坡又是墙，取决于坡度）。

### 第 3 步 · 落脚面积（关键：不能只测一个点）

以 `(x, z)` 为中心，按**脚底尺寸**（human 0.6×0.6，写进能力表）取 **4 角 + 中心共 5 个采样点**，逐点求候选面：

- 至少 **3/5** 落在**同一个面**上 → 通过（允许一只脚踩空一点，符合走边缘的真实感）
- 全部落在同一面 → `overhang = 0`
- 3/5 或 4/5 → `overhang = 0.2 / 0.4`，**仍可站立但报"站不稳"**（供 UI 弱提示）
- 全部落空 → `reason: "no-surface"`

`overhang` 是**给导演看的诊断量**，不是物理量。它让"这个位置人会站在悬崖边上"这件事可见。

### 第 4 步 · 头顶净空

从落脚面顶面往上 `loco.height + clearanceMargin`（默认余量 0.15m）的区间内，不允许任何对象的 `[bottom, top]` 与之相交（`occluding`/`blocking` 无关，纯几何）。

不满足 → `reason: "no-clearance"`，UI 文案「这里站不直」。这是"走在矮桌下面必须弯腰 / 干脆走不过去"的实现方式。

### 第 5 步 · 语义

`walkable === false` → `reason: "not-walkable"`。水面可以**经过**（y 取水面高度，报"涉水"），但不算"站立支撑"。

## 6. 移动判定：沿路径连续采样

```ts
export interface WalkLegResult {
  ok: boolean;
  /** 第一次失败的路径里程比例 0..1（供 UI 定位）。 */
  failureAt?: number;
  reason?: StandResult["reason"] | "gap";
}

export function walkLeg(
  state: DirectorState,
  a: Vec2, b: Vec2,
  fromY: number,
  loco: Locomotion,
): WalkLegResult
```

算法：

1. 沿 `a → b` 以固定步长采样（默认 0.15 m，与脚底尺寸同量级）
2. 每步调 `standable`，`fromY` 滚动更新为上一步的 `y`（保证连续走下坡时"够得着"下一段）
3. 任一步失败 → 记下里程，返回 `reason`
4. **"gap"** 单独归类：连续两步的落脚面高度差落在 `(maxStep, maxJumpHeight]` → 不是"站不住"而是"需要跳"（详见 [02](./02-跳跃与攀爬.md)）

**台阶的迈步处理**：`Δh ∈ (0, maxStep]` 时 y 是**离散跃变**（不是平滑上升）。视觉上两层平滑：

- **y 时间低通**：复用 `solver.ts:517-548` 的指数低通写法，时间常数 ~0.08s → 身体不会一格一格地弹
- **步态相位对齐**：`HumanoidRig` 已有 `phaseRef`（`WorldView.tsx:309`）随速度累加。台阶处按"每级一步"重置相位，让抬腿与上台阶同步，避免脚在半空踩空

> 第二点是"像不像在走楼梯"和"像在飘"的分界线，值得单独做。

## 7. 25 个 case 判定矩阵

| # | Case | 几何条件 | 判定 | 结果 | UI 提示 |
|---|---|---|---|---|---|
| 1 | 平地行走 | `Δh = 0` | — | 贴地 | 无 |
| 2 | 上台阶 | `0 < Δh ≤ maxStep` | 可达 | 贴地（离散跃变 + 低通） | 无，自动迈步 |
| 3 | 下台阶 | `−maxStep ≤ Δh < 0` | 可达 | 贴地 | 无 |
| 4 | 上坡 | 连续 `Δh ≤ maxStep`，坡度 ≤ maxSlope | 可达 | 贴地（连续） | 无 |
| 5 | 下坡 | 同上反向 | 可达 | 贴地 | 无 |
| 6 | 连续楼梯 | 每级 ≤ maxStep | 逐级可达 | 贴地 + y 低通 + 步态对齐 | 无 |
| 7 | 陡坡 | 坡度 > maxSlope | 不可走 | **退化为墙** → 水平阻挡 | 走现有绕行 |
| 8 | 高台（够不着） | `Δh > maxStep` 且超跳跃能力 | 不可达 | 水平阻挡 | 走现有绕行 |
| 9 | **跳上高台** | `maxStep < Δh ≤ maxJumpHeight` 且 `dx ≤ reach(Δh)` | 跳跃可达 | `vertical: parabola` | **「需跳跃」**+弧线+一键生成 |
| 10 | 跳得太高 | `Δh > maxJumpHeight` | 不可达 | 阻挡 | **「太高，跳不上去」** |
| 11 | **跳过沟** | `Δh ≈ 0`，中间不可站立（洞/水），`dx ≤ reach(0)` | 跳跃可达 | `vertical: parabola` | **「需跳跃」** |
| 12 | 跳下（落差） | `Δh < −maxStep` | 下落 | `vertical: fall` | **「下落 x.x m」** |
| 13 | **攀爬** | `maxJumpHeight < Δh ≤ maxClimbHeight` 且有竖直抓手 | 攀爬可达 | `vertical: climb` | **「需攀爬」** |
| 14 | 完全不可达 | `Δh > maxClimbHeight` | 不可达 | 阻挡 | **「不可达」**+路径断开警示 |
| 15 | 堆叠站立 | 上层 `baseY = 下层 top`（相切） | 可达 | 站上层 | 无 |
| 16 | 桥下穿行 | `bottom ≥ fromY + height + clearance` | 可通行 | 贴地走（水平不挡） | 无 |
| 17 | 桥下净空不足 | `bottom < fromY + height` | 阻挡 | 绕行 | 走现有绕行 |
| 18 | 站边缘（部分悬空） | 3/5 或 4/5 采样点在面上 | 可站 | 站立 + 报不稳 | **「站不稳」**（弱，灰） |
| 19 | 脚底全悬空 | 全部采样点落空 | 不可站 | 落回 / 报错 | **「这里踩不到」** |
| 20 | 头顶净空不足 | 上方对象 `bottom < 落脚面 + height` | 不可站 | 判 blocked | **「这里站不直」** |
| 21 | 水面 | `walkable: false` | 不可站但可经过 | `y = 水面高度` | 可选「涉水」 |
| 22 | 被推入障碍 | 惯性甩动把队员推进盒子里 | 现有二次兜底 push-out | 推出 + **重算 y** | 无 |
| 23 | 组队过坎 | 锚点需要跳 | 各成员在自己弧长处各自跳 | 全部 `parabola` | 徽标只画锚点弧上 |
| 24 | 相机跟跳 | FOLLOW 一个跳跃目标 | 相机 y 剧烈变化 | 需垂直防抖 | 见 [03 §10](./03-UI可达性提示.md#10-相机跟跳的防抖) |
| 25 | planar 老场景 | `worldMode === "planar"` | `maxStep=0`、无跳跃、无攀爬 | **逐像素不变** | 无 |

### 矩阵里最容易被漏掉的四个

- **#7 陡坡与 #8 高台是同一个几何的两种命运** —— 都是"上不去"，但一个因为坡度、一个因为落差。两者都退化为水平阻挡，**共用现有的绕障路径**，不需要新逻辑。
- **#11 跳过沟** 是唯一"Δh 为零但必须跳"的情况。它证明跳跃判定**不能只看高度差**，必须看"路径上是否存在连续可站立面"。
- **#18 / #19 的区别只有采样点数量** —— 这正是为什么站立判定必须做多点采样而不是查一个点。
- **#22 被推入障碍** 的 `pushOut`（`pathfinding.ts:38-50`）在 3D 下推出后**必须重算 `baseY`**，否则人会悬在半空。而且推出目标本身要是"可达面"，否则推到一个 Δh 超标的位置，人还是站不住 → 需要迭代（上限 8，与 `separateSetAsset` 的迭代数一致）。
